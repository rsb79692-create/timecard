# devicewatch — 施設端末の持ち出し監視アプリ（iOS / Android）

施設に置いてある打刻用スマホが施設の範囲外へ持ち出されたときに、管理者へ LINE 通知を出すための
**極小アプリ**。勤怠アプリ（timecard）をネイティブ化したものではない。

## このアプリがやること／やらないこと

| やること | やらないこと |
|---|---|
| 施設端末としての登録（8桁コード） | 打刻・勤怠一覧・スタッフ一覧・帳票 |
| 位置情報「常に許可」の要求と状態表示 | 履歴画面（このアプリは履歴を持たない） |
| OSのジオフェンス（範囲外・範囲内）の受け取り | 持ち出しの判定そのもの（サーバが判定する） |
| 位置と権限状態のサーバへの報告 | LINE の送信（サーバが既存基盤で送る） |

**判定・重複抑止・通知はすべてサーバ側（`api/device-report.js` と `api/_lib/device.js`）にある。**
アプリを書き換えても判定を変えられないようにするため、意図的にアプリへ置いていない。

個人データは一切扱わない。端末に残るのは `deviceId` / `deviceToken` / 施設の基準位置だけ。

## ファイル

| ファイル | 内容 |
|---|---|
| `src/watch.js` | 登録・報告・ジオフェンス・権限判定。ロジックはすべてここ |
| `App.js` | 画面1つだけ（登録コード入力 / 状態表示）。JSX を使わず `node --check` できる形にしてある |
| `app.config.snippet.json` | `app.json` へマージする権限・背景モードの設定 |

★ **`package.json` を置いていない。** 依存の版は SDK に合わせて `npx expo install` が決める。
ここに版を固定すると、SDK と不整合な版が入ってビルドが通らない／背景位置が動かない。

★ **署名資格情報を commit しないこと。** このリポジトリは GitHub Pages がリポジトリ直下を
配信するため、commit した鍵は誰でもダウンロードできる。`.gitignore` に
`*.keystore` / `*.jks` / `*.p8` / `*.mobileprovision` / `credentials.json` /
`google-services.json` / `GoogleService-Info.plist` / `eas.json` / `*.apk` / `*.aab` / `*.ipa`
を入れてあるが、**ビルド設定に秘匿値を書かない**（環境変数は EAS Secrets に置く）のが本来の統制である。

## 運用手順

1. 管理画面（timecard）→ マスター管理 → 拠点トークン管理 → 対象施設の「▼ 端末持ち出し監視」を開く
2. 監視ONにして「保存」。基準位置が分かっていれば緯度・経度を入れる
   （施設内で操作しているなら「この端末の現在地を入れる」でよい）
3. 「端末の登録コードを発行」を押す（有効期限24時間・1台ぶん）
4. 施設のスマホでこのアプリを開き、コードを入力 → 位置情報を「**常に許可**」
   （基準位置が未設定なら、登録した場所が基準位置になる）
5. 管理画面の同じ場所で「監視中」と最終受信時刻を確認する
6. **下の「★ 定期実行の設定」を済ませる**（これが無いと自動では通知されない）

## ★ 定期実行の設定（これが無いと自動では通知されない）

⚠ **2026-09-13 時点で①②はどちらも未登録である。** つまり現状は「端末が次に報告したとき」か
「管理画面を開いたとき」しかスイープが走らない。**端末が1台だけの施設では、管理画面を開くまで
通知が出ないことがある。** 下の2つを設定すると解消する。

「範囲外へ出て3分」を確定させるのはサーバ側のスイープで、外部スケジューラが1分間隔で叩く。

### ① Vercel の環境変数

| 名前 | 値 | 環境 |
|---|---|---|
| `DEVICE_SWEEP_KEY` | **32文字以上**のランダム文字列（32文字未満は拒否される） | Production |

作り方（**必ず暗号論的乱数で作る**。**生成した値をチャットや議事録へ残さないこと**）:

```bash
# Node（このリポジトリで使っているので確実に入っている）→ 43文字
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

```powershell
# PowerShell でもよい → 約42〜43文字（"+/=" を除去するため長さは乱数で変動する）
$b=[byte[]]::new(32); [System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); ([Convert]::ToBase64String($b) -replace "[+/=]","")
```

★ **`Get-Random` や `Math.random()` で作ってはならない。** どちらも暗号論的乱数ではなく、
32文字あっても実効的な強度は32bit程度まで落ちる（下記のとおり総当たりに耐えるのは鍵だけなので、
長さだけ揃えても意味がない）。

登録したら**必ず再デプロイする**（環境変数は起動時に読まれる）。

★ **なぜ32文字以上が必要か。** このリポジトリは GitHub Pages が直下を配信するため、
URL・`action` 名・フィールド名・403/503 の意味はすべて公開されている（秘匿に頼らない設計）。
そのうえ鍵の誤りには**レート制限が掛からない**（鍵の照合を RTDB より前に置いているため）。
総当たりに耐えるのは鍵の長さだけである。

### ② cron-job.org のジョブ

| 項目 | 値 |
|---|---|
| URL | `https://timecard-rho.vercel.app/api/device-report` |
| メソッド | `POST` |
| 実行間隔 | **毎分** |
| ヘッダ | `Content-Type: application/json` |
| Body | `{"action":"sweep","key":"<①で決めた値>"}` |
| 通知 | **2xx 以外で通知を有効にする**（止まったことに気づける唯一の手段） |

### 鍵を変えるとき（漏れた・cron-job.org のアカウントを移す等）

セッションを持たず冪等なので、次の順で止まらずに入れ替えられる。

1. Vercel の `DEVICE_SWEEP_KEY` を新しい値へ更新 → **再デプロイ**
2. cron-job.org のジョブの Body を新しい値へ更新

★ 1と2のあいだは 403 になり、そのあいだだけ定期実行が止まる（保険の経路は動き続ける）。
★ 鍵を変えても端末の再登録・アプリの更新は要らない（アプリは鍵を持たない）。
★ 鍵は外部サービス（cron-job.org）のジョブ本文に平文で保管される。**アカウント自体の保護
（強固なパスワード・2要素認証）を優先すること。**

### 設定できたかの確認

```
{"ok":true,"devices":1,"sent":0,"confirmed":0,"confirms":0,"stales":0,"unjudged":0}
```

- `200` ＋ 上記の JSON … 正常（`devices` は登録済み端末の台数）
- `503 sweep_not_configured` … ①が未登録／32文字未満／再デプロイしていない
- `403 forbidden` … 鍵が違う（★ 前後の空白と改行は無視されるので、それが原因ではない）
- `400 bad_json` … **Body が JSON として読めていない。** 応答の `hint` で原因が分かる:

  ⚠ **本番の Vercel では本文の中身をサーバ側から読めない**ため、hint は実質
  `len=~N-M head=unread` だけになります（2026-09-13 実測）。**長さで切り分けます。**

  鍵の長さを `L` とすると:

  | 本文 | バイト長 | 例（L=43） |
  |---|---|---|
  | 正しい JSON `{"action":"sweep","key":"…"}` | **27 + L** | 70 → `len=~64-79` |
  | form 形式 `action=sweep&key=…` | **17 + L** | 60 → `len=~48-63` |

  → `hint` の長さが **27+L より約10バイト短い**なら、Body が **form 形式**になっています。

  直し方（どの場合でも有効）: cron-job.org のジョブを開き、

  1. 「POST変数」「キー/値」のような**表形式の入力欄は空にする**
  2. **リクエスト本文（Request body）の欄**へ、次の1行を**そのまま**貼る
     ```
     {"action":"sweep","key":"<①で決めた値>"}
     ```
  3. ヘッダに `Content-Type: application/json` があることを確認する
  4. 保存して、実行履歴が **200** になることを確認する

  ★ 引用符は**半角の `"`**（全角 `”` は不可）。末尾にカンマを付けない。`{` で始めること。
  ★ `hint` に本文の内容（鍵）は含まれません。16バイト単位へ丸めた長さだけです。
  ★ 本文を送っていない場合は `bad_json` ではなく `400 bad_action` になります。
- `400 bad_action` … Body の `action` が `"sweep"` でない（本文は JSON として読めている）
- `415 unsupported_media_type` … `Content-Type` が `application/json` でない

## Android 実機での確認手順

★ **Expo Go では背景位置・ジオフェンスが動かない。** 必ず development build か内部配布ビルドを使う。
★ 上の「定期実行の設定」を先に済ませること。済んでいないと 5. で待っても LINE が来ない。

### 1. Android へ監視アプリを入れる

```bash
# 上の「セットアップ」を済ませたプロジェクトで
npm i -g eas-cli
eas login
eas build:configure
eas build --platform android --profile preview     # 内部配布 APK
```

ビルドが終わると EAS が配布 URL を出す。**その URL を Android 端末のブラウザで開いて APK を入れる**
（「提供元不明のアプリ」の許可を求められたら許可する）。Play ストアへ上げる必要はない。

USB で繋いだ端末へ直接入れるなら:

```bash
eas build --platform android --profile preview --local   # ローカルで APK を作る
adb install -r <できた .apk>
```

### 2. 施設端末として登録する

1. PC で管理画面（timecard）→ **マスター管理** → **拠点トークン管理** → 対象施設の **「▼ 端末持ち出し監視」**
2. **監視ON** にして **保存**。基準位置が分かっていれば緯度・経度を入れる
   （施設の中で操作しているなら「この端末の現在地を入れる」でよい）
3. **「端末の登録コードを発行」** を押す（8桁・24時間・1台ぶん）。★ コードはこの1回しか表示されない
4. Android 端末でアプリを開き、そのコードを入力して登録
5. 管理画面の同じ場所に端末が並び、**最終受信**の時刻が入ることを確認する

### 3. 位置情報を「常に許可」にする

アプリが順に要求するので、**ダイアログでは必ず上の選択肢を選ぶ**。

| 端末の画面 | 選ぶもの |
|---|---|
| 「位置情報へのアクセスを許可しますか？」 | **アプリの使用中のみ許可** → 続いて背景の要求が出る |
| 「常に許可に変更しますか？」 | **設定を開く** → **常に許可** |

あとから確認・変更するときは
**設定 → アプリ → devicewatch → 権限 → 位置情報 → 常に許可**、かつ
**正確な位置情報（Precise / 高精度）をON**にする。

★ 「アプリの使用中のみ許可」のままだと、アプリを閉じた時点で報告が止まる。
その状態はサーバが検知して**管理者へ LINE で通知**し、管理画面にも「権限に問題あり」と赤く出る。
★ **電池の最適化から除外**しておく（設定 → アプリ → devicewatch → バッテリー → 制限なし）。
制限されていると Android が背景タスクを起こさず、報告が遅れる。

### 4. 150m 以上持ち出す

許容半径の既定は **150m**。**余裕を見て 300〜500m 離れる**（GPS 誤差を差し引いて判定するため、
ちょうど 150m では確定しない）。**屋外を歩いて移動する**こと（屋内・地下・車内は測位が粗くなる）。

アプリを開いて「最終報告」の時刻が進んでいれば報告は届いている。

### 5. 3分後に LINE が届くことを確認する

```
【施設端末 持ち出し検知】
<施設名>
9/13 20:15
施設の設定範囲外へ移動しました。
```

★ **「範囲外になってから3分後ちょうど」には来ない。** サーバは「最初に範囲外を受け取った時刻」から
3分以上経ってから確定するので、**3〜5分**を見ておく。
★ 端末の電源を切っても届く（経過はサーバ受信時刻で測っている）。電源を切って試すなら、
**範囲外の報告が1回届いたあと**（アプリで最終報告の時刻が更新されたあと）に切ること。

届かないときの切り分け:

| 症状 | 見るところ |
|---|---|
| 5分待っても来ない | cron-job.org の実行履歴が 200 か（503/403 なら上の「定期実行の設定」） |
| 同上 | 管理画面で「監視中（緑）」か。「基準位置が未設定」「判定待ち」「権限に問題あり」なら原因はそれ |
| 同上 | 管理画面の端末行の**直近の距離**。150m 以下なら単に離れ足りない |
| LINE 自体が来ない | 朝の未打刻通知が届いているか（届かないなら LINE 側の設定の問題） |

### 6. 範囲内へ戻す

施設へ戻る（屋外で数分待つ）。管理画面の表示が **「監視中」** へ戻ることを確認する。
★ **復帰の LINE は出さない**（仕様）。内部状態だけが戻る。

### 7. もう一度持ち出して、再通知されることを確認する

4〜5 をもう一度行う。**2通目が届けば「復帰後は再通知される」ことが確認できた**。

★ 逆に、**範囲内へ戻さずに持ち出しを続けているあいだは2通目が来ない**（同一持ち出し中は1回だけ）。
これも仕様どおりの挙動なので、混同しないこと。

## 検知の性質（誤解しないこと）

- **通知は「範囲外になってから3分後ちょうど」には来ない。** サーバは「最初に範囲外を受け取った時刻」から
  3分以上経ってから確定する。判定は1分間隔の定期実行（および次の報告）で行うため、実際は **3〜5分**になる。
- **同じ持ち出し中に何度も通知しない。** 範囲内へ戻ると内部状態が戻り、次の持ち出しで再び通知する
  （復帰そのものは通知しない）。
- **範囲外を1回報告した直後に端末が沈黙しても（電源を切る・機内モード・OSが起こさない）、
  サーバ側のスイープが3分の経過を見て確定する。** 経過はサーバ受信時刻で測るので、
  端末の追加報告は要らない。スイープは**外部スケジューラから1分間隔で走る**ため、
  **管理画面を誰も開かなくても通知される**（上記「★ 定期実行の設定」）。
- **iOS は静止している端末への背景実行を保証しない。** そのため「一定時間受信なし」の検知は
  しきい値 24 時間で、あくまで補助である。確実な検知手段ではない。
- **位置情報を切られた・アプリを消された場合は、その時点では検知できない。**
  アプリが次に起動・復帰したときに権限の異常を報告する。それも無ければ受信途絶として現れる。
- **報告は届くのに位置が判定できない状態**（位置を送らない・測位が粗すぎる）も、
  しきい値を超えると「位置を判定できません」として通知し、管理画面に赤く出る。
  検知が死んでいるのに正常に見える状態を作らないため。
- **位置そのものは端末の自己申告である。** 判定をサーバへ置いた目的は重複通知の抑止と
  端末時刻の偽装対策であって、位置の真正性の保証ではない。改造クライアントや OS の位置偽装で
  「範囲内」を偽ることはできる（ただし上記のとおり痕跡は残る）。
- **端末の電源を切って範囲外へ出る前から沈黙した場合は検知できない。** OSの機能を使う以上これは避けられない。

## サーバ側

| 場所 | 役割 |
|---|---|
| `POST /api/device-report` | このアプリ専用（`register` / `report`）＋定期実行（`sweep`・共有鍵で認証）。Origin を送らないので CORS ヘッダは返さない |
| `POST /api/device` | 管理画面専用（管理者ロールのみ） |
| RTDB `/devmon` | 設定と端末の状態。`database.rules.json` に未定義＝クライアントから到達不能 |
| LINE 通知 | 既存の Messaging API push（`LINE_CHANNEL_ACCESS_TOKEN` / `LINE_TO_ID`）を再利用 |
