## マルチテナント（複数の会社で共用）— 2026-09-26

**1つのコード・1つの Firebase プロジェクトを、株式会社 穂乃味とマンテール株式会社（以降も追加可）で共用する。**
会社ごとの違いは「会社設定」と「機能フラグ」だけで表し、**会社ごとにコードを複製・分岐しない**。
共通機能の変更は1回の実装で全社へ反映される。

★ **本番反映済み（2026-09-26）**: Firebase Rules（database・storage）を c42db49 の内容で deploy し、取り直して一致を確認した。
変更前の本番 Rules はリポジトリ外 `Projects/rules-backup-20260926-192911/` に保存してある（rollback 用）。
`/tenantReg/mantel`（`active:false`）と `/srv/mantel/authz/_meta` は firebase CLI（ユーザーのログイン）で作成した。
**PIN の値（`/authz/systemAdminPin`・`/srv/mantel/authz/adminPin`）はサーバ経由でだけ作る**（下記「PIN の初回設定」）。
★ **honomi-board リポジトリの `database.rules.json` は、この時点で本番と一致していない**（`tenants` と `/honomi` の他社トークン拒否が無い）。
ボード側から Rules を deploy する前に、必ず本番の現行 Rules を取り直してマージすること（本書「RTDB のルールは honomi-board と共有」）。

  あわせて画面の会社設定の `facilityAdminMenu`（施設URLの打刻トップに管理者メニューを出すか）を決める。

### 会社間の遮断（画面だけでなく DB・API・Storage で遮断する）

| 層 | 遮断の方法 |
|---|---|
| トークン | 新会社のトークンはクレーム **`c`（会社ID）と `sx`（業務上の期限）** を持つ。穂乃味のトークンは**従来と同一**（`c` を持たない。uid も従来どおり `a:main` / `s:<キー>`） |
| API | 全ハンドラを `T.handler` で包む。会社は `body.tenant`（未指定＝穂乃味）で選び、**`verifyIdToken` がトークンの会社とリクエストの会社の一致を検査**する（不一致は署名が正しくても無効＝401）。DB のパスは `google.js` が会社コンテキストから1か所で写す。**会社コンテキストが無いまま DB に触れると例外**（穂乃味へ倒さない） |
| RTDB Rules | `/tenants/$cid` は `auth.token.c === $cid` ＋ `sx` 未失効 ＋ `/tenantReg/$cid/active === true`。**読み取りも書き込みもコレクションごとの許可リスト**（会社ノード直下に `.read` を置かない＝親で許可すると下位で取り消せないため）。トークン類（閲覧用・デモ・スタッフテストURL）の一覧は管理者だけ、個別の1件はその役割だけ。許可外のノード・打刻の全消去・PIN フラグの書き込みは拒否。`/honomi` には「他社のトークン（`c` が honomi 以外）を拒否する」条件だけを足した（穂乃味のトークンの判定は変わらない） |
| Storage Rules | 新会社は `tenants/<cid>/documents/…`・`tenants/<cid>/staff_uploads/…`。`c` と `sx` を検査。穂乃味のパスは他社のトークンを拒否 |
| 端末 | localStorage は会社別の接頭辞（`t.<cid>.`。穂乃味は従来のキー名）、IndexedDB（未送信打刻）は `timecard_punch_outbox__<cid>`。**穂乃味の保存内容をマンテールの画面が読むことはない** |

★ **利用停止は二重チェック**: API の入口（`T.handler` が `/tenantReg/<cid>/active` を確認。5秒キャッシュ）と Rules（毎回参照）。
Storage のルールは RTDB を参照できないため、停止後もトークンの `sx`（最長24時間）までは Storage だけ読める。**Storage を即時に止めたい場合はこの時間差を認識すること。**
⚠ **今後のセキュリティ改善項目（未対応）**: 利用停止後も Storage が最長24時間読める。即時に止めるには、Storage のアクセスをサーバ経由（署名付きURL等）にするか、停止時にその会社のユーザーの refresh token を失効させる仕組みが要る。

### PIN の初回設定（鍵はサーバにしか無いので、サーバ経由でだけ作る）

`TC_PIN_PEPPER` / `TC_ENC_KEY` は Vercel の Sensitive 型で、手元に控えが無い（`vercel env pull` でも値は取れない）。
PIN レコードはこの2つで作る必要があるため、**PIN の値はすべて `/api/auth/admin-pin-set` で作る**。⚠ **この2つを変更・再生成してはならない**（穂乃味の全PINが照合できなくなる）。

| 操作 | 誰が | 条件 | 画面 |
|---|---|---|---|
| システム管理者PINの初回設定（`scope:"system"`） | 穂乃味の管理者（sa 不要）。**いまの管理者PIN（`currentPin`）の再入力が必須**＝管理者URLだけを知る人は設定できない | `/authz/systemAdminPin` が**未設定のときだけ**。`if-match: null_etag` の条件付き書き込みで1回だけ成功し、設定済みなら 409。いまの管理者PINの照合は管理者ログインと同じレート制限の枠（`admin_ip` / `admin_all`）。管理者PINと同値は 400。レコードに設定元（`setBy`: uid・セッション時刻）を残す | マスター管理タブの「システム管理者PIN（未設定）」（サーバが未設定と答えたときだけ出る） |
| システム管理者PINの変更（`scope:"system"`） | sa を持つセッション（`?sys` でログイン中） | **いまのシステム管理者PIN（`currentPin`）の再入力が必須**（照合は管理者ログインと同じレート制限の枠）。穂乃味の管理者PIN・各社の管理者PIN・いまのPINと同値は 400。`systemAdminMinAt` を進め、**変更前の全社のシステム管理者セッションを失効**させる（変更した本人は新しいPINで張り直す）。`setBy.via:"change"` を残す。穂乃味の `?sys` でも他社の `?c=…&sys` でも変更できる（照合・書き込みは常に穂乃味の `/authz`）。回数制限のリセットは書き込みの成功後だけ。⚠ 変更直前30秒以内（`ADMIN_AT_SKEW_SEC`）に発行されたシステム管理者セッションは失効しない。**漏えいを疑って変更するときは、30秒以上たってからもう一度変更する**。sa でログイン中は、既存の管理者PIN欄（`scope` なし）でもシステム管理者PINと同値は 400（sa の無い通常の管理者には照合しない） | マスター管理の「システム管理者PINを変更」（sa のときだけ表示）。このとき既存の管理者PIN欄の見出しは「穂乃味の管理者PIN変更」（他社の画面では「<会社名>の管理者PIN変更」）になる。通常の管理画面は変わらない |
| 他社の管理者PINの設定（`scope:"tenantAdmin", target`） | 穂乃味側のシステム管理者セッション（穂乃味の `?sys` で入る。他社の `?c=…&sys` 画面ではボタンを出さない） | 対象会社の `/srv/<会社>/authz/_meta` が在ること（無ければ 503）。**停止中の会社にも設定できる**（停止中は入口で全 API が 403 のため、その会社のセッションからは設定できない）。システム管理者PIN・穂乃味の管理者PINと同値は 400。設定すると `adminMinAt` でその会社の以前の管理者セッションを失効させる | 利用会社の管理の各社行「管理者PINを設定」 |

⚠ システム管理者PINが未設定のあいだは、**穂乃味の管理者PINを知っている人なら最初の1回を設定でき、その人が全社の管理権限を持つ**。
設定後はこの経路は閉じる（409）。未設定のまま放置しないこと。`/authz/systemAdminPin` を消すとこの経路が再び開く。
★ 未知の `scope` は 400（自社の管理者PINの変更へ落とさない）。`op:"systemPinStatus"` は値が何かあれば「設定済み」を返す（条件付き書き込みの判定と揃える）。
★ システム管理者PINのログインは、穂乃味の管理者ログインと**同じレート制限の枠**（`admin_ip` / `admin_all`）を使う。別枠にすると総当たりの速度が倍になる。
⚠ システム管理者PINは「全社の管理」への入口なので、会社管理者PINとは別の値にし、知る人を限ること。
★ システム管理者でも「穂乃味として得たトークン」で他社の API は叩けない（会社ごとに入り直す）。

### マンテールは穂乃味の弱い方式を引き継がない

- **匿名サインインを一切使わない。** 起動時は次のどれかで会社ID付きのトークンを取ってから読む。
  施設URL（`?c=mantel&token=<施設トークン>` → 施設端末トークン `r:"k"`）／管理者URL／閲覧・デモ・スタッフテストURL／どれも無ければ管理者PIN入力で待つ。
- 施設URLの打刻トップにも、穂乃味と同じ上部の「管理者メニュー」（会社管理者PIN画面へ）を出す。穂乃味は施設URLでは出さない（2026-10-13 ユーザー指示。穂乃味に揃えて消さない）。
  この違いはコードの分岐でなく会社設定 `TENANT_CONFIGS.<会社>.facilityAdminMenu` で表す（会社を足すときに決める）。
- 施設URLがあるのに認証サーバへ一時的に届かないときは、管理者PIN画面へ落とさず「サーバに接続しています」画面で**間隔を空けて自動再試行**する（5秒から倍々・最大5分。利用停止中は5分間隔）。
  施設トークンが無効（401）なら端末の保存を消し、そのページでは二度と試さない（施設の共有IPのレート制限枠を使い切らない）。
- 業務上の期限（`sx`）が切れたとき: 施設端末・スタッフは施設URLで施設端末トークンを取り直す。**管理者・閲覧・デモは黙って施設端末へ下げず、ログインし直してもらう。**
  ⚠ 施設端末トークン（`k`）は打刻を書けないため、スタッフの期限切れ後に端末に残った**未送信打刻は次のスタッフがログインするまで送られない**（消えはしない。10分超で既存の「未送信の打刻があります」警告が出る）。
- 施設端末トークン（`k`）が読めるのは PIN 画面までに要る最小限（スタッフ一覧・部門・施設マスタ・PIN登録済みフラグ・打刻）だけ。**書き込みは一切できない**（打刻はスタッフのログイン後）。
- **スタッフPINは端末に置かない。** `/tenants/mantel/tc5_pins` は「登録済みか」の真偽だけで、照合・登録・確認（管理者の「PIN確認」）はすべてサーバ（`/api/auth/pin-set`・`/api/auth/staff`）。
  ★ そのため**マンテールでは打刻画面へ入るのに認証サーバ（Vercel）への接続が要る**（穂乃味は従来どおり）。
- PIN のキーは `hash("tenant:"+会社ID+"\0"+氏名)`。**会社をまたいだ同姓同名で衝突しない**。穂乃味のキーは従来の `hash(氏名)` のまま（既存スタッフにPIN再設定を求めない）。
- ★ 穂乃味の匿名読み取りの穴（本書「残っている穴」）は**今回は変更していない**（ユーザー指示。別工程で扱う）。

### 管理画面を閉じたときの権限の解除（穂乃味・他社で共通。2026-10-13）

管理者URL・管理者PINのどちらで入っても、管理画面の「← 閉じる」（`closeAdminMenu`）は**管理者の権限を解除してから**打刻トップへ戻る。
処理は穂乃味・他社で共通（`adminSessionRelease` / `adminSessionDrop`）で、違うのは「戻り先の通常セッション」だけ。

| 端末 | 閉じた後のセッション |
|---|---|
| 穂乃味 | 匿名セッション（従来の起動経路と同じ。保存済みがあれば復元） |
| 他社・施設URL（施設トークン）のある端末 | 施設端末トークン（従来の起動経路と同じ。再読み込みしない） |
| 他社・施設URLの無い端末（管理者URL・管理者PINで入った端末） | 管理者セッションをサーバで交換した施設端末トークン（`/api/auth/share` の `kind:"adminKiosk"`）。打刻トップに全スタッフが出るのは管理者URLの端末だけで、管理者PINで入った施設URLの無い端末は従来どおり「このURLからは打刻できません」＋管理者メニュー |

- ★ 閉じた後は `isAdminAuthenticated`・`isSystemAdmin` を落とし、管理者トークンをメモリから捨てる（端末へは元々保存していない）。
  **打刻ログインと PIN 新規登録は各スタッフの PIN で行い、管理者トークンで送らない**（送ると登録済みの他人の PIN を上書きできる）。
  閉じた後の「管理者メニュー」は管理者PIN画面へ進む（管理者URLのトークンで黙って入り直さない）。
- ★ `adminKiosk` の交換: 管理者の ID トークン（`r:"a"`・`adminSessionValid` で失効していない）だけを受け付け、`r:"k"`・`ka:true`・施設キー（`fk`）無し・期限 `sx` は元の管理者セッション以下のトークンを出す。
  書き込みは一切できない（施設端末トークンと同じ Rules）。穂乃味では 401（匿名で戻るため）。端末へは保存しない（`_saveAnonSession`・`_restoreAnonSession` が `ka` を除く）。
  通信できずに交換できなければ閉じない（管理画面のまま「通信できないため…閉じられませんでした」）。サーバが拒否した（401/403＝失効・期限の残り15分以下）ときは権限を落として閉じる（失敗を管理者の権限を残す側に倒さない）。成功したら `share_ip` の数を戻す。
  解除の通信の間は画面全体を「閉じています…」で覆い、管理画面を操作させない。
- ★ 管理者URL（URL に施設トークンが無い）を正規に認証できた端末は、打刻トップに全スタッフを出す（`adminUrlAll`。`?token=all` と同じ表示。端末保存の施設トークンに左右されないので PC とスマホで同じ）。
  端末へは保存しない。管理者URLの認証が通らなければ出さない。打刻は各スタッフの PIN が要る（管理者URLだけで全施設の打刻ができるようにはしない）。
- ★ 管理者URLのタブで閉じた後は、再読み込み（アプリの自動更新を含む）でも管理画面へ戻さない（`sessionStorage` の記録＋ナビゲーションの種類）。
  戻すと、閉じて放置した端末が自動更新のたびに管理者の権限を取り戻す。管理者URLを**新しいタブ**で開けば従来どおり管理画面（同じタブで同じ URL を開き直すとブラウザは再読み込みとして扱うため打刻トップのまま。管理者PINでも入れる）。
- 保存の通信・承認の保留書き込みの途中は閉じない（「保存中です」）。解除すると書き込めなくなるため。
- ⚠ 管理者URLはそれ自体が資格情報で、知っている人（ブラウザの履歴を含む）は開けば管理者になる。共用端末で管理者URLを開いたままにしない運用は従来どおり必要。
- 他社で施設URLの無い端末の施設端末・スタッフのトークンが期限（`sx`）切れになったら、取り直す元が無いので「ログインし直してください」で再読み込みしてもらう（管理者URLなら再認証して打刻トップへ戻る）。
- テスト: `node tests/visual/admin-close.js`（穂乃味・マンテール × スマホ・PC）／`node scripts/test-multitenant.js` の「6b」。

### ブランド（会社設定）

- 色は CSS 変数（`--brand` ほか）。`:root` の既定値が穂乃味の色。`--brand` 系（PINの決定ボタン・管理画面のタブなど）は穂乃味の従来の青のまま（トップ画面の五十音タブの選択色だけは `--sel-bg` に分けてロゴ色にした）。
- 2026-10-08 から、穂乃味の**装飾の色**（ページ背景・カード・枠・表見出し行・見出しの下線・本文・見出し文字・補足文字）を公式ロゴに合わせた（`--page-bg` `--card-bg` `--card-border` `--head-bg` `--head-bg2` `--head-line2` `--title-line` `--bar-line` `--text` `--heading` `--muted`、トップ画面の部品用に `--btn2-bg` `--btn2-text` `--btn-border` `--sel-bg` `--date-text`）。スタッフ側の画面の補助ボタン（管理者メニュー・もどる・PINのテンキーと取消）、トップ画面の五十音タブ（選択中を含む）とスタッフボタンの枠もロゴ色にした（打刻ボタン `.btn-in` 等と PIN の決定ボタンは変えていない）。打刻ボタン・PIN の決定ボタン・管理画面のタブと、成功・警告・エラーの色、文字サイズは変えていない（スタッフ側の補助ボタン・五十音タブの選択色は前の文のとおり変えた。レイアウトはロゴの分だけ変わる）。そのため `tests/visual/visual-regression.js` は、この変更より前のコミットと比べると穂乃味の画面で差分が出る（意図どおり）。以後の変更の確認は、この変更以降のコミットを比較元にする。
- ★ **会社を足すときは、`theme` に上の装飾の16変数も入れる。** 入れないと `:root` の既定値＝穂乃味のロゴ色を継承する（マンテールは従来の白・灰色の値を入れてある）。
- 穂乃味のロゴ（2026-10-08）: `brand/honomi/logo-h108.png`（公式ロゴの白い余白だけを詰めて縮小。図柄は変えない）。高密度画面用に `logo-h240.png` を srcset で出し分ける。表示は `honomiLogoHtml(高さ, 位置のクラス)` だけで行い、高さは画面幅で自動調整する（スタッフ選択＝日付・時計の左に横並び 44〜78px（画面幅と文字の大きさから算出。標準の文字なら幅約350px以上で78px。収まらないときはロゴが上の行に回る）／打刻画面＝「もどる」の行の右 50〜58px／管理者メニュー見出しの左 44〜48px／管理者PIN＝見出しの上 48px）。★ `TENANT.legacy`（穂乃味）のときだけ返すので他社には出ない。他社のロゴは従来どおり `tenantBrandHeaderHtml` / `tenantBrandBarHtml`。★ 打刻ボタンの色・形・大きさ・並びは変えない（ロゴの分だけ打刻画面で10〜18px下がる）。width/height（縦横比）を先に決め、読み込めないときは場所を保って隠す。
- マンテール: ロゴ（`brand/mantel/`。元画像 1181×1181 を縦横比 1:1 のまま 160/320/180/192/512px の PNG へ最適化）・会社名・主色 `#B40000`（ロゴの赤）・背景白。`manifest-mantel.json`（`id` を分けて別アプリとしてインストールされる）。
- ★ **出勤の色（`--punch-in`）と土曜日の青は会社で変えない。** 「出勤＝青／退勤＝赤」「土＝青／日＝赤」の区別なので、赤がブランド色の会社で赤くすると見分けられなくなる。
- 機能フラグ（`features`）: マンテールは **移動距離・端末持ち出し監視を無効**（穂乃味の施設間距離表・専用アプリが前提のため）。
  **賄い（`meals`）も無効**（2026-10-13 ユーザー指示「マンテールの感染症と賄いの機能は非表示」）: 退勤時の賄いの質問・打刻画面の賄いカード・「CSV出力」の賄い一覧と日次/月次CSV・プレビューの賄いの列・スタッフ編集の「賄い 要」・閲覧用の「この月の賄い回数」とその CSV 列を出さない。
  欄を出さない会社では、スタッフの保存で既存の `mealRequired` を変えない。データ（`tc5_meals`）は消さない。衛生・感染症の確認は月次書類（`monthlyDocs`。穂乃味専用）の一部で、マンテールでは元から動かない。
  確認: `node tests/visual/tenant-features.js`。有効化は会社設定の値を変えるだけ（サーバ側も同じ値で API を拒否している）。

### 通知

| 通知 | 会社ごとの分離 |
|---|---|
| アップロード通知（`/api/line-notify`・`/api/discord-notify`） | 宛先は環境変数 `<名前>` + `__<会社ID大文字>`（例 `DISCORD_WEBHOOK_URL__MANTEL`）。**未設定なら送らない（穂乃味の宛先へ倒さない）**。新会社はログイン中のトークン必須 |
| 持ち出し検知（`api/_lib/device.js`） | 同上の環境変数。定期スイープは全社を回し、各社のコンテキストで判定・送信（機能が無効な会社・停止中の会社は回さない） |
| 朝の未打刻（`scripts/morning-check.js`） | `TENANT_ID` 環境変数（未指定＝穂乃味＝従来どおり）。施設・判定時刻・除外施設・見出しは `MORNING_TENANTS`。**マンテールは施設と判定時刻が決まるまで `enabled:false`**。送信記録は `/srv/<cid>/morningNotify` |
| 通知確認（`scripts/notify-check.js`）・FCM（`scripts/fcm-check.js`） | `TENANT_ID` 環境変数。FCM の通知には会社IDが入り、`sw.js` がその会社の画面へ遷移する |

★ ワークフロー（`.github/workflows/`）は**変更していない**（穂乃味は従来どおり）。マンテールの定期通知を動かすには、`TENANT_ID=mantel` のジョブと `__MANTEL` の Secrets の追加が要る（人間の確認が必要）。

### 本番反映の手順（★ ユーザーの確認後に行う。Agent が勝手に行わない）

1. 本番の現行 Rules を取得して保存（バックアップ）し、リポジトリの `database.rules.json` と**ボード側・穂乃味側の差分が無いこと**を確認する（差分があればマージしてから）
2. `firebase deploy --only database`・`--only storage`（honomi-board と同居のため全体置換。手順1が必須）
3. 取り直して照合。穂乃味の打刻・管理画面・ボードの動作を確認
4. Vercel に `__MANTEL` の通知用環境変数（必要な分）を登録
5. `/tenantReg/<会社>`（`active:false`）と `/srv/<会社>/authz/_meta` を作る。
   `TC_PIN_PEPPER` / `TC_ENC_KEY` の控えがあれば `node scripts/bootstrap-tenant.js --tenant <会社>`（dry-run）→ `--apply`。
   控えが無ければ firebase CLI で上の2つだけを作り（PIN 関連は書かない）、PIN は下の6で画面から設定する（2026-09-26 のマンテールはこの方法）
6. システム管理者PIN（未設定なら穂乃味の管理者が初回設定）→ `?sys` で入り、利用会社の管理から対象会社の管理者PINを設定
7. 会社間分離を本番で実測 → system_admin が利用開始にする → その会社の管理者PINで入り、施設・スタッフを登録

**rollback**: 穂乃味のデータは一切変えていないので、コードの revert と Rules を手順1の保存版へ戻すだけでよい。
マンテールだけを止める場合は `/tenantReg/mantel/active=false`（システム管理者画面から可）。
