## 管理者による勤怠編集（未打刻の日の新規作成・2026-09-07）

管理者は**出勤・退勤の打刻が1件も無い日でも**、時刻セルをクリックして入力し、
勤怠レコードを作成できる（スタッフ別詳細＝月別の職員別勤怠画面／勤怠一覧＝日別画面のどちらでも）。

打刻レコードは**1打刻＝1ノード**（`/tc5_records/{id}`）で、打刻が無い日はレコードが存在しない。
したがって未打刻の保存は既存レコードの更新ではなく**新規作成**になる（`index.html` の `save()` の
`else` 枝が `generateRecordId()` で採番して PUT する）。この経路は変更前から存在した。

★ 旧実装ではスタッフ別詳細だけが `hasData`（その日の打刻が1件以上）を編集セルの描画条件にしていたため、
打刻ゼロの日は編集できなかった。2026-09-07 にこの条件を外した。

### 未取得の月では未打刻セルを編集させない（★外してはならない）

スタッフ別詳細は `mRecsStaff`＝**メモリ上の `records`** しか見ておらず、`ensureAdminRecordRanges()` は
非同期で取りに行くだけで描画を待たない。したがって月を切り替えた直後・通信が遅い端末では、
**サーバに打刻がある日も「−」に見える**。

そこで入力すると、`save()` の重複防止（`records.find(...)`）が**メモリ検索なので空振り**し、
同じ日に2つ目の `clockIn` ノードができる。`calcMs()` は時系列走査で `cin` を後勝ちに上書きするため、
**実働時間＝賃金の基礎が変わる**（承認漏れ集計・月別出勤日数・有給付与日数の自動算出にも波及）。

★ 特に危険なのは**当月**である。起動時に取得済みなのは当日だけ（`loadPunchRecords()`）なので、
月半ばに当月を開くと「当日だけ打刻あり・それ以前は未打刻」という**もっともらしい画面**になり、
過去月の全日空欄と違って気づけない。

そのため `var monthKnown=recordsMonthKnown(selMonth);` を判定し、偽のあいだは

・未打刻セル（`rec` なし）を**非編集の「−」に落とす**
・テーブル上部に赤バナーを出す（`AGENTS.md`「未取得の期間を『0件』と誤認させない」に従う）

打刻済みセル（`rec` あり）は `data-id` を持ち上書き更新になるため、未取得でも編集してよい。

### 表示（勤怠一覧と表現をそろえる）

以下は**スタッフ別詳細の中での規約**である。勤怠一覧（日別）は休憩ペアが0件のときに
下線の無い `--:-- → --:--` を非編集で出すため、`−`＝入力できない、は画面をまたいでは成立しない。
判別の実体は**下線の有無と `time-cell` クラスの有無**である。

| 表示 | 意味 |
|---|---|
| `08:30` ＋下線 | 打刻あり。クリックで修正できる |
| `--:--` ＋下線 | 未打刻。**クリックで入力できる** |
| `−`（下線なし） | **入力できない**（承認済みの日／この月が未取得／当日より後の日） |

★ 表示文字は `--:--` か `−` のどちらかにすること。`attachTimeCellHandlers()` は
`if(cur==="--:--"||cur==="−")cur="";` でこの2つだけを空欄として扱う。他の文字にすると既存値として拾われる。

★ 勤怠一覧（日別）の未打刻セルと同じ表現（`--:--` ＋実線）にそろえてある。
この画面だけ別の表現（破線・`min-width` など）にしてはならない。同じ操作が2画面で別に見える。

★ 休憩列は td 側の `hasData?brkDisplay:'<span>−</span>'` を `brkDisplay` へ単純化した。
編集可否は `dBrkPairs.length>0` のままなので**実挙動は変わらない**（打刻ゼロの日は非編集の `−`）。
打刻ゼロの日の休憩セルの見た目が、打刻はあるが休憩が無い日と揃うだけである。

### 当日より後の日は編集させない（★外してはならない）

`recMonthEnd()` は**当月の取得上限を当日で丸める**。したがって当月の「明日〜月末」は
どの経路でも取得されず、未来月は `recordsMonthKnown()` が無条件で真を返す。
つまり `monthKnown` が真でも、**当日より後の日は「未取得」である**。

端末時計が進んだ端末の打刻など未来日付のレコードは実在しうるため、ここを開けると
上と同じ二重ノードができる。そこでガードは `if(!rec&&(!monthKnown||dk>recToday()))` とし、
**当日より後の未打刻セルも非編集の `−`** にしている。
打刻済みセルは `data-id` を持つため未来日でも編集できる（上書き更新なので重複しない）。

★ 勤怠一覧（日別）には `selDate` に対する同種のガードが無く、取得完了前や未来日で
同じ二重登録が成立しうる（本変更より前からの既存の穴。今回は触っていない）。

### 管理者の出勤・退勤修正と同時承認（2026-09-27）

管理者が時刻セルで**出勤・退勤**を修正・入力し、修正理由を選んで［確定］すると、
その保存と同時にその日（`approvals[date+"__"+氏名]`）を承認済みにする。別途［承認］を押す必要はない。

・対象は `attachTimeCellHandlers()` の出勤・退勤だけ（既存打刻の修正と、未打刻からの新規作成の両方）。
　休憩の修正・削除・「➕ 打刻を追加」・職員本人の打刻・修正申請の承認・一括承認は**従来どおり**（承認しない）。
・承認するのは、承認ボタンと同じ `validateAttendanceRecord()` を通る日だけ。
　退勤漏れ・出勤漏れ・勤務時間異常の日は**時刻だけ保存**し、理由を短く表示する。
　未打刻の日に出勤→退勤と続けて入力した場合は、退勤を確定した時点で承認される。
・修正理由・`editHistory`・`editedFrom`・`original*`/`corrected*` は従来どおり記録する。
　同時承認した時刻を `adjustApprovedAt` として打刻レコードに残す。
・過去データ・既存の承認は一括変更しない（変更後に管理者が確定した日だけ）。

★ 時刻と承認は `saveRecordWithApproval()` の**1回の多パス更新**（`PATCH {FB_URL}.json` に
`tc5_records/{id}` と `tc5_approvals/{key}` の2パス）で書く。RTDB の多パス更新は全パス成功か全パス失敗のため、
「時刻だけ保存」「承認だけ保存」にならない。**この経路で `saveApprovals()`（`tc5_approvals` の全体PUT）を使ってはならない。**
★ ルート直下への更新なので、`rec.id` が `^[A-Za-z0-9_-]{1,128}$` でなければ書かない（空 id で `tc5_records` 全体を置き換えないため）。
★ 保存に失敗したときは、メモリ上の承認・修正した打刻・新規に積んだ打刻を元へ戻し、端末保存も書き直す（画面を「保存されていない」状態と一致させる）。
★ 職員名に RTDB のキーに使えない文字（`. # $ [ ] /` と制御文字）があると承認を保存できないため、出勤・退勤の修正自体を保存しない。

承認後はその日が読み取り専用になる（下記4）。確定後にさらに直すときは、従来どおり先に引き戻す。

### 既知の制限（未解消・運用で認識しておくこと）

1. **管理者が作成した出勤打刻は `workFacility` を持たない。**
   `index.html` の新規レコード生成は `{id, staff, type, date, time, timestamp, manualAdd, editedByAdmin, ...}` だけで、
   施設を入れない（管理者が入力していない値を推測で埋めないため）。結果として
   ・`calcMsByFacility()` の施設別按分・応援集計で施設が空になる
   ・移動距離の自動集計で**起点未確定（`no_origin`）**になる
   　（★ **その日に施設変更（応援）打刻がある場合に限る**。`mileageAutoDayRoute` は
   　`if(!b.hasMove)return out;` で、移動が無い日は `status:"none"` として確定を止めない）
   ★ **止まるのは「その職員」ではなく「その月」全体である。**
   `closeMonth` は年月単位で全職員を計算し、`comp.unresolved > 0` なら 409 `unresolved` を返す
   （`api/mileage.js`）。**1職員・1日の要確認で、その月の確定が全職員ぶん止まる。**
   「その人だけ後回しにする」ことはできない。
   復旧は「打刻に無い移動の手入力（例外）」を職員が登録し管理者が承認する経路だけである
   （打刻修正申請の承認では `workFacility` が入らないため解消しない。移動距離の節を参照）。
   ★ **管理者は代理で手入力を作成できない。** `ACTIONS.saveRequest` は `["s"]`（職員ロールのみ）
   なので、打刻を作った管理者が自分で後始末できず、必ず当該職員のログインが要る。
   ★ 既存レコードの `workFacility` を後から設定できる管理UIは存在しない。
   これは日別画面からの作成でも同じ既存挙動だが、月内全日ぶんの導線が増えたぶん発生しやすい。

2. **休憩は時刻セルからは新規作成できない。**
   スタッフ別詳細・日別一覧のどちらも `dBrkPairs.length>0` / `brkPairs.length>0` のときしか
   編集セルを描画しない。休憩打刻が1件も無い日に休憩を足すには、
   管理画面の**「➕ 打刻を追加」フォーム**（`breakStart` / `breakEnd` を選べる）を使う。
   1組できれば以後は時刻セルから編集できる。
   ★ `calcMs()` は既定の休憩控除を持たず、実在する `breakStart`/`breakEnd` の差分しか引かない。
   打刻忘れの日に 08:30〜17:30 だけを入れると**実働 9:00（休憩0分）**で確定する。
   休憩の入力漏れに注意すること。**既定の休憩控除を実装で足してはならない**（既存の計算ルールを変えない）。

3. **管理者デモ（`?demo=`）ではこの経路に到達できない。**
   `_applyDemoUiLock()` が全 `.time-cell` に `pointer-events:none` を付け、
   「➕ 打刻を追加」も `DEMO_BLOCK_SELECTORS` の `#btn-add-rec` で `disabled` になる。
   なおコード上は `records.push(nr)` が `saveRecord()` の `demoWriteBlocked()` より前にあるため、
   将来この UI ロックを外すと幻のレコードが次のポーリングまで画面に残る（`_lsSet` には到達しない）。

4. 承認済み（`approvals[dk+"__"+nm]`）の日は従来どおり読み取り専用。編集するには先に引き戻す。

5. **未取得の月では、サマリー（出勤日数・総実働時間・残業時間）と「一括承認」が
   取得済みの日だけを対象にする**（本変更より前からの既存挙動。`totalMs` 等はメモリ上の
   `records` から計算し、一括承認も `monthKnown` を見ていない）。
   誤読を防ぐため赤バナーを**サマリーバーの上**へ置き、集計値がまだ確定でないことを明記している。
   ★ この順序を入れ替えてはならない。数字を先に読ませると「出勤日数1日」を確定値と受け取る。
