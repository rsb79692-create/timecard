## 直した不具合（2026-09-29 まで）

管理画面の `staffList`（`tc5_staff`）と `masterFacilities`（`master/locations`）は起動時に1回読むだけで、10秒ごとの同期でも取り直さない。
それなのに、1人を編集・追加・削除しただけでも、手元の古い一覧で**配列全体を PUT** していた（`saveData("tc5_staff",staffList)` / `saveFacilities()`）。
そのため、開いたままの古い画面から保存すると、他の端末や CSV一括登録が後から追加したスタッフ・施設や、他の人への編集が黙って消えていた。

## 今の保存のしかた（★変えてはならない）

保存のたびに最新を取り直し、**変える1件の添字だけ**に書く。配列という構造（添字をキーにしたノード）は変えない。

| 操作 | 書き込み |
|---|---|
| スタッフの編集 | 最新の一覧で同名・改名の判定をしてから、その人の添字へ PUT。フォームに無い項目は最新の値を保つ |
| スタッフ・施設の追加 | 末尾の次の添字へ「無ければ書く」条件付き PUT（`if-match: null_etag`）。先に使われていたら（412）取り直し、同名を再確認して次の添字へ |
| スタッフ・施設の削除 | 末尾の1件を消した行の添字へ移し、末尾を消す（1回の PATCH＝全部成功か全部失敗）。**配列に空き（null）を作らない**。添字が変わるのは末尾の1件だけ |

- ★ 配列に空きを作らないのは、空きがあると RTDB が **null 入りの配列**（まばらならオブジェクト）を返し、更新前の版の画面が読み込みで止まるため。
- それでも空きのある値を読んだとき（手作業の変更など）に備え、読み込み（起動時の端末保存の控えを含む）は `mstToList()` で null を読み飛ばす。サーバ（`api/_lib/secrets.js`・`api/auth/share.js`）と `scripts/morning-check.js` も null を読み飛ばす。
- 改名時の打刻・承認・PIN の氏名の付け替えは、スタッフ行の保存が成功してから行う（保存に失敗したときに食い違わない）。
- 編集と削除は、書く直前にその添字の行がまだ同じ人・施設（`name` が一致）かを1件だけ取り直して確かめ（`mstSame`）、違えば書かずに「他の端末で同時に変更された」と知らせる（削除で末尾の行が移った直後に、別人の行へ書かないため）。
- 最新を取得できない・形式が想定外のときは書かない（フェイルクローズ）。書き込みに失敗したらモーダルを閉じず、画面の一覧を最新へ戻す。
- デモ・テスト画面（`writePolicy!=="full"`）は従来の経路のまま（書き込みは `saveData` / `authFetch` 側で遮断・模擬）。

## 残っている全体保存・既知の制限

- `tc5_staff` / `master/locations` の全体 PUT は、デモ・テスト画面の経路と、起動時に「施設マスタが本番に無い」ときの初期書き戻し（`initFirebase`）だけ。
- 同じ人を2つの端末で同時に編集した場合は、後から保存した方が勝つ（その人の行だけ。他の人の行には影響しない）。
- 編集は、書く直前の確認（`mstSame`）から PUT までのごく短い間だけ条件付きではない。その間に他の端末が同じ人を削除・移動すると別の行へ書きうる。確認を通った後に同じ人の内容が変わっていた場合は、後から保存した方が勝つ。編集の PUT を ETag の条件付きにしていないのは、ブラウザから ETag 応答ヘッダを読めるか未確認のため。
- 削除の PATCH も条件付きではない。確認から PATCH までのごく短い間に、別の端末が末尾へ追加すると配列に空き（null）が一時的に戻り（新しい版は読み飛ばす）、末尾の行を編集すると移した先に編集前の内容が入りうる。どちらも管理者2人の同時操作でだけ起きる。
- 更新前の版のアプリは、これまでどおり古い一覧で全体 PUT する。自動更新（`app-shell-cache.md`）で全端末が新しい版になるまでは、古い画面から保存すると消えうる。
- 部門マスタ（`tc_master_depts`）・承認（`tc5_approvals`）・穂乃味の `tc5_pins` は、今回の対象外で全体 PUT のまま。
