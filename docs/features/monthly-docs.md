## 現場の操作

| 場面 | 出るもの | 条件（手元の当日の打刻 `records` だけで判定） |
|---|---|---|
| 出勤 | 衛生・新興感染症（1画面・問題なし／問題あり） | 本人のその日の記録が無い |
| 出勤の確定後 | 朝の温度 | 施設の朝（slot 0）が未記録、かつ12時より前 |
| 退勤 | 日中の温度 | 12時より前に出勤した人（日中勤務）で、最後の退勤者でない、日中（slot 1）が未記録 |
| 退勤 | 夕方の温度 | 12時以降に出勤した人（夕方勤務）、または最後の退勤者。夕方（slot 2）が未記録 |
| 退勤 | 保存食（はい／いいえの1問） | 最後の退勤者で、施設のその日の「はい」が未記録 |

- **最後の退勤者** = その施設に本人以外の勤務中（`getCurrentWorkFacility` がその施設）の人がいない。ただし日中勤務の人は16時以降に限る
  （夕方勤務が後から来る施設で、昼の退勤を最後と誤らないため。時刻は補助条件）。タイムカードに勤務区分は無い（2026-10-07 調査）。
- 問題あり → 「責任者に連絡してください」で打刻しない。端末に `mdoc.ng.<日付>.<氏名>` を残し、開き直した出勤では聞かずに打刻して `hyg:{a:"ng"}` を記録する（スタッフへの説明表示はしない）。
- 保存食「いいえ」→ 確認済みにしない（記録は `no`、帳票のサインは空欄）。「責任者に連絡してください」の後に退勤する。次の最後の退勤者にまた聞く。
- 廃棄対象日 = 保存日の15日前（元Excel 食事記入表 A7。月次書類 `HOZON_OFFSET_DAYS` と同じ）。
- ★ **出勤は「問題なし」を押した時点で確定する**（2026-10-09 ユーザー指示。その時刻が出勤時刻）。朝の温度は出勤の条件にしない。
  出勤を端末に保存して画面を打刻済みにした後で、朝の温度の画面（「出勤しました HH:MM」）を続けて出す。「記録しないで閉じる」・放置3分・通信できない場合も出勤はそのまま。
  ★ **出勤は「問題なし」の時点で端末保存し、すぐ送る**（2026-10-09 追加指示。朝出勤確認で未出勤と誤らないため。出勤の送信を温度のために止めない）。
  朝の温度は出勤とは独立した記録: 端末保存の付属エントリ（`kind:"mdocTemp"`・`eventId` = 出勤の `eventId`+`~t`）にして、出勤がサーバに届いてから その出勤の `mdoc/temp` だけへ PUT する
  （`_punchOutboxDue` が出勤の未送信中は送らない＝出勤の無いノードに温度だけを作らない。再送は打刻と同じで、2回目以降は存在確認して上書きしない。再送では出勤のノードがあることも確かめ、無ければ送らずに終える。出勤の他の項目・管理者の修正に触れない）。
  出勤がまだ一度も送信を試していない（別の送信の順番待ち等。`pending` かつ `retryCount` 0）ときだけ、温度を出勤レコードへ同梱する。通信できずに出勤の送信が一度失敗していれば付属のエントリになり、出勤が届いた後に送る。温度を端末に保存できなければ知らせる（出勤は記録済み）。
  未送信の温度は `punchOutboxMergeInto` でその出勤の表示に重ねる（他の人に同じ朝の温度を聞かない）。打刻としては積まず、「未送信の打刻」の件数にも数えない。
  温度の画面には誰の出勤かを出す（共用端末で別の人が入れないため）。温度の画面は開いてから3分で閉じる（操作しても延びない。共用端末をふさがない）。
  朝の温度を記録しないまま閉じた日は、12時より前に出勤する次の人に再び聞く。月次書類の温度管理表（6:30 の欄）でも手入力できる。
- 二重打刻: `doPunch` の検査に加え、確認画面を閉じた後に同じ人の同じ打刻が手元の記録に届いていないかを `doPunch` と同じ規則で見直す（通信なし）。
- 温度: 温度計を見て数字だけを入れる（冷凍のマイナスは画面で固定）。前回値は参考として小さく出すだけで入力欄には入れない。値の無い機器があるうちは記録ボタンを押せない。
  記録ボタン（出勤後は「温度を記録」、退勤は「記録して退勤」）を押したことが実測の確認。
- 退勤は従来どおり、日中・夕方の温度と保存食をすべて答えてから、回答と退勤を一緒に端末へ保存して確定する（「やめる」は退勤しない。退勤の時刻は退勤ボタンを押した時刻）。

## データの流れ

1. `_execPunch` の端末保存の**前**に `mdocPlan` → `mdocCollect`。回答は打刻レコードの `mdoc`（`{f:施設, hyg:{a}, temp:{s,d:[{id,k,n,o,v}]}, hozon:{a,store,discard}}`）。
   打刻と同じ IndexedDB 保存・`eventId` への PUT・再送に乗る（打刻と監査記録が分かれない）。「やめる」は打刻しない。
   出勤の朝の温度だけは出勤の確定後（`mdocAfterClockIn`）に、独立した付属エントリとして送る（上記「現場の操作」）。
2. 送信成功時（`punchOutboxFlush` の成功、`rec.mdoc` あり）は `POST /api/monthly-docs {action:"sync",days:2}`（当日と前日。3秒まとめ）、起動時（30分に1回まで）は `days:7`。会社全体でも10分600回まで。
3. サーバは直近2日または7日の `tc5_records` を `date` 索引で取得し、`tc5_staff`・`master/locations` と並列に読んで `eventsFromRecords` で検証 →
   月次書類 DB の `tc_ingest`（500件ずつ）。`event_id` = `eventId:種別` の一意制約で再送・重複しても1件。
   衛生は（氏名×日）、温度は（施設×日×時間帯）、保存食「はい」は（施設×日）でも DB が一意にする（2人同時の最終退勤でも1件）。
4. 測定対象（施設別マスター）は月次書類 DB の `temp_devices`。`action:"devices"` で取得して端末（`TLS` の `mdoc.dev.<施設>`）に控える。
   取り直しは起動時（施設端末）とスタッフ選択時に裏で、30分以上たっていれば。確認画面は控えがあれば古くてもすぐ使い（取り直しは裏）、控えが無いときだけ取得を待つ（トークン取得を含めて6秒で打ち切り、温度なしで打刻できる）。

## 通信回数（打刻1回あたり）

- 聞くものが無い打刻（大半）: 追加の通信 0・追加の await 0（`mdocPlan` は手元の配列を見るだけ）。
- 確認画面を出す打刻: 画面表示のための通信 0（控えがあるとき）。送信成功後に sync 1回（3秒まとめ。結果を待たない）。
  出勤の確定までの待ちは「問題なし」の1押しだけ（温度の入力を待たない）。出勤は確定と同時に送る（PUT 1回）。朝の温度を記録したときだけ、`mdoc/temp` への PUT が1回と転記（sync）が1回増える（出勤が送信の順番待ちで同梱できたときは増えない）。回答（衛生・温度・保存食）の無い送信では転記を頼まない。
  ⚠ この方式（付属エントリ `mdocTemp`）より前の版へ戻すと、旧版は `kind` を知らず未送信の付属エントリを打刻として `/tc5_records/{id}~t` へ送ってしまう。戻すときは、戻す版で `kind` を持つエントリを捨てる処理を入れてから配信する。
- 他社: 0（関数の入口で終わる）。

## 安全

- Supabase の service role key は使わない。Vercel に置くのは 公開キー（`MDOC_SUPABASE_KEY` は `sb_publishable_` 以外を拒否）・URL・合言葉 `MDOC_INGEST_KEY`（32文字以上。DB にはハッシュだけ）。
- anon に許すのは `tc_ingest` と `tc_devices` の実行だけで、合言葉が無ければ例外。表への権限は無い。
- クライアントから記録の内容を受け取らない（sync はサーバが RTDB の打刻を読む）。本人は打刻の氏名が `tc5_staff` にあること、施設は `master/locations` にあり、出勤はその打刻の施設、退勤はその日の本人の打刻に現れた施設（応援先を含む）であることを検査。削除された打刻・施設の項目が無い打刻は転記しない。
  ⚠ 打刻（`tc5_records`）は匿名でも書ける既存の穴（`rtdb-access.md`）があり、監査記録の真正性は打刻の真正性と同じ水準である。
- 記録は追記のみ（内容は誰も更新・削除できない）。誤った記録は月次書類の画面で「取り消し」の印だけ付けられる（一方向。取り消すと一意制約の対象から外れ、正しい記録が入れる）。月次書類側の手修正は `sheet_cells` に書かれ、`change_log` に変更前・変更後・変更者・日時が残る。
