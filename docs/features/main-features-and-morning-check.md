## 主要機能

- **打刻**: Realtime Database `tc5_records`（`index.html`）。端末（IndexedDB）へ保存してから非同期送信（下記「打刻の端末永続保存と自動再送」）。
- **打刻修正申請**: `tc5_correction_requests`。承認は `tc5_approvals`。未対応申請は FCM Push で通知（`scripts/fcm-check.js`）。
- **有給**: 申請 `tc5_paid_leave_requests`、残数 `tc5_paid_leave_balances`。付与・承認時にスタッフ本人へアプリ内通知（直近コミットで実装）。
- **月別出勤日数**: `tc5_monthly_days_import`（`scripts/fix-monthly-days-year.js` は年度補正用の保守スクリプト）。関連: ルートの `勤務日数管理.xlsx`。
- **ピン留め等**: `tc5_pins`。
- **通知系**:
  - 朝出勤確認 LINE通知（`scripts/morning-check.js`、`.github/workflows/morning-check.yml`、**判定時刻ごとに1日2回**）
    - **未打刻の判定時刻は施設ごとに持つ**（2026-09-11 追加）。6時の回と7時の回で対象施設が排他に分かれるため、同じ施設へ二重通知されない。
      - 現在の割り当て: **ハルイロ / ミュゲの泉 = 7時**、その他 = 6時（ハーベストは従来どおり `NOTIFY_EXCLUDE` で通知対象外）。
      - ⚠⚠ **判定時刻の正本は `morning-check.js` の `LATE_CHECK_FACILITIES`（コード側）である。施設マスタ側には持たせない。**
        `master/locations` は `/honomi` の `.write` を継承し、管理者だけでなく**一般スタッフ（`auth.token.r === 's'`）でも書ける**。
        そこへ判定時刻を置くと、6時の回の直前に「全施設=7時」、7時の回の直前に「全施設=6時」と書き換えるだけで、
        **その日の未打刻通知を1件も出さずに Actions を success のまま終わらせられる**（画面に出ないフィールドなので誰も気づけない）。
        移動距離申請が `master/locations` をサーバ側の判断材料にしていないのと同じ理由。施設マスタは「どの施設が在るか」の正本としてだけ使う。
      - 施設マスタの施設名との突き合わせは `normalizeFacility`（NFKC＋空白除去）で行い、`LATE_CHECK_FACILITIES` に書いた施設名が
        マスタに見当たらない場合は `findMissingLateFacilities` が `[WARN]` を出す（改名・表記ゆれの検知）。
      - 有効な判定時刻は `CHECK_HOURS = [6, 7]` だけ。`CHECK_HOUR` が不正なら**既定へ倒さず `exit 1`**（黙って6時として走ると、6時の施設へ二重通知しつつ7時の施設が誰にも判定されない）。
      - ⚠ **`CHECK_HOURS` へ時刻を足すときは `morning-check.yml` の cron も必ず足す。** cron の無い時刻を指定した施設は誰にも判定されず、通知が消える。
        この対応は `scripts/test-morning-check.js` が `CHECK_HOURS` から導出して機械的に検証する。
      - ⚠⚠ **`scripts/morning-check.js` の `DEFAULT_FACILITIES` と `index.html` の `DEFAULT_FACILITIES` は
        同名だが役割が違う。同期してはならない。**
        `index.html` 側は**空配列**である（実施設名を配布物へ埋め込まないため）。
        一方 `morning-check.js` 側は ①施設マスタを取得できなかったときのフォールバック、
        ②`expectedFacilityCountForHour()` が使う「この判定時刻に何件在るはず」の期待値、の2役を持つ。
        施設マスタは一般スタッフでも書けるので、期待値だけは改ざんされない場所に置く必要がある。
        - `morning-check.js` 側を空にすると `expected` が常に 0 になり、`selectedCount < expected` が永久に偽になって
          **施設を全部消されても「設定異常」を検知できなくなる**（下記の監視が無言で無効化される）。
        - `index.html` 側へ実施設名を書くと、**配布物へ施設名が埋め込まれる**。
        - **施設が増減したときは `morning-check.js` 側を更新する。** 理由の詳細は同ファイル冒頭のコメントを参照。
      - **監視が黙って落ちないようにしてある**（2026-09-11）。施設マスタの改名・削除・件数異常で「対象0件 → 静かに正常終了」になると、
        その日の未打刻通知が消えたことを誰も知れないため、次はログではなく **LINE へ「設定異常」通知**を送る:
        - `LATE_CHECK_FACILITIES` の施設名が施設マスタに見当たらない（改名・表記ゆれ・削除）
        - コード側の期待件数（`DEFAULT_FACILITIES` から導出）が 1 件以上あるのに、その回の対象が 0 件

        施設マスタが `MAX_FACILITIES`（50件）を超えた場合は採用せず `DEFAULT_FACILITIES` へ倒す（黙って切り詰めない）。
      - 施設名は LINE 本文とログへ入る前に `safeFacilityLabel()` を通す（改行・制御文字・ゼロ幅・双方向制御の除去、URL スキームの無害化、40コードポイントで切り詰め）。**照合には使わない**（照合は `normalizeFacility`）。
      - ⚠⚠ **これで「朝通知の抑止」が防げるようになったわけではない。** `tc5_records` の `.write` は `auth != null`（**匿名でも可**）なので、
        施設ごとに偽の `clockIn` を1件ずつ書けば、その日の未打刻通知は今も消せる。打刻自体を止められない以上ここは塞げず、既存リスクとして許容している。
        判定時刻をコード側へ移したのは、**画面に一切現れない隠しフィールドで**同じことができる状態を作らないため、という限定的な目的である。
      - どの回かは起動経路（cron 式 / `inputs.checkHour`）から決めて `CHECK_HOUR` で渡す。**実行時の現在時刻からは決めない**（下記の遅延のため、6時の回が7時台に走ると6時の施設が飛ばされ7時の施設へ二重通知される）。未知の cron 式ならワークフローが `exit 1` する。
    - ⚠⚠ **時刻どおりの通知は cron ではなく外部スケジューラからの `workflow_dispatch` が担っている**（2026-09-11 実測）。
      `schedule` の cron は**このリポジトリでは全く当てにならない**:

      | 指定 | 実際の起動（直近10日・UTC） | 遅れ |
      |---|---|---|
      | `"3 21 * * *"`（21:03 UTC） | 22:48 / 22:51 / 22:58 / 23:04 / 23:08 / 23:12 / 23:14 / 23:14 / 23:18 / 23:25 | **1時間45分〜2時間22分** |

      過去には 8時間遅れも観測されている（2026-08-28）。`fcm-notify` は30分間隔指定に対し1日数回しか走っておらず、**取りこぼしも起きている**。
      PUBLIC リポジトリの scheduled run は GitHub 側の負荷で遅延・ドロップされるためで、こちらでは制御できない。
      - **6時分**: 外部スケジューラが毎日 **21:03:03 UTC ちょうど**に `workflow_dispatch`（`inputs` 空 → 6時判定）。これが確実な経路。
      - **7時分**: 外部スケジューラ（**cron-job.org**）に **22:03 UTC / `inputs: {"checkHour": "7"}`** を登録済み（2026-09-11 にユーザーが登録）。
      - **確認済み（2026-09-11 実測）**: cron-job.org と同じ REST ペイロード
        （`POST /repos/.../actions/workflows/{id}/dispatches` に `{"ref":"main","inputs":{"checkHour":"7"}}`）で
        本番の `morning-check.yml` を起動し、`判定時刻: 7時（決定元: inputs.checkHour）` → 7時の対象2件で完走することを確認した。
        **ワークフロー側の写像は検証済み**である。
      - **未確認（2026-09-11 時点）**: cron-job.org が実際に 22:03 UTC に撃つかどうか。
        **初回発火は 2026-09-12 07:03 JST（= 2026-09-11 22:03 UTC）**で、それまで観測できない。
        初回発火後に `判定時刻: 7時（決定元: inputs.checkHour）` を1度だけ目視確認するまで、
        「登録済みで稼働確認済み」と扱わない。
        - 確認コマンド: `gh run list --workflow=morning-check.yml --limit 10 --json event,createdAt,conclusion`
          → 22:03 UTC 付近に `workflow_dispatch` の行が出ていること。
          `gh` が使えない場合は https://github.com/rsb79692-create/timecard/actions を見る。
      - ⚠ **登録値は文字列 `"7"` ちょうど**であること。誤った値の壊れ方は2種類あり、**どちらも LINE には何も出ない**
        （`morning-check.js` へ到達しないため `findMonitoringAnomalies` も働かない）:

        | 登録値 | 何が起きるか | どこで気づけるか |
        |---|---|---|
        | `"07"` / `" 7 "` / `"6.0"` 等の文字列 | run は作られ、allowlist（`case "${HOUR}" in 6\|7`）が `exit 1` | **Actions の run が赤くなる** |
        | JSON 数値 `7`・真偽値など非文字列 | GitHub API が `422 Invalid value for input 'checkHour'` を返し、**run が作られない**（2026-09-11 実測） | Actions には何も出ない。**cron-job.org 側の実行履歴（HTTP ステータス）でしか気づけない** |
      - `morning-check.yml` の cron 2本は、外部スケジューラが止まったときの取りこぼし防止（遅れてでも通知する）として残す。**時刻の正確さを cron に期待しない。**
      - ⚠ **起動は「常時二重化」である。** 外部スケジューラが正常な平常時も cron は毎日起動しており
        （上の実測表がその記録）、定常状態は **判定時刻2種 × 各2 run ＝ 1日最大4 run**。
      - ★ **それでも LINE は「同一日 × 同一施設 × 同一判定時刻で最大1回」である**（2026-09-13 実装）。
        2回目以降の実行は、通知記録を見て**通知済みの枠を送らない**。cron と外部スケジューラは**どちらも外してはならない**
        （片方にすると、その経路が止まった日に通知が消える）。以前の「同じ枠で2通目が届くのは既知・許容」は**破棄した**。

        | 項目 | 内容 |
        |---|---|
        | 記録 | RTDB ルート直下 **`/morningNotify/{判定対象日}/h{判定時刻}`**（1ノード）。`database.rules.json` に未定義＝**クライアントから読み書き不可** |
        | ベース URL | ⚠⚠ **`FIREBASE_DATABASE_URL` のオリジン**（`dedupeBaseUrl`）。この Secret は `.../honomi` で終わるので、そのまま（`FB_DB_URL`）使うと `/honomi/morningNotify` になり、**一般スタッフが「送信済み」を書いて通知を止め、再送用の本文を差し込める**。判定データ（`tc5_records` / `master/locations`）だけが `FB_DB_URL` を使う |
        | 枠 | 施設名（`normalizeFacility` 後）の SHA-256 先頭32桁。設定異常は `anomaly` という枠 |
        | 書き手 | GitHub Actions のサービスアカウント（`FIREBASE_SERVICE_ACCOUNT_KEY`。fcm-notify / notify-check と同じ Secret） |
        | 競合 | ノード全体を **ETag の条件付き書き込み（`if-match`）で1回に確保**する。同時に走った実行は片方だけが確保でき、もう片方は 412 で読み直す |
        | 送信中の実行 | 送信権は10分のリース。他の実行が送信中なら**リースが切れるまで（最大11分）待ち**、切れたら同じ要求を引き継いで再送する。待ち切っても送信中なら `exit 1` |

        **LINE 送信失敗時の再試行方針**（実装は `scripts/morning-check.js` の `MORNING-CHECK-DEDUPE` ブロック）

        | LINE の応答 | 扱い | その後 |
        |---|---|---|
        | 200 / 409 | `sent` | 以後その枠は送らない。409 は「同じ retry key が受付済み＝もう届いている」 |
        | 500系 / 429 / タイムアウト / 通信断 | 送れたか分からない（`retry`） | 同じ実行内で 2秒 → 6秒 あけて**同じ本文・同じ `X-Line-Retry-Key`** で計3回。だめなら **次の実行が同じ要求をそのまま再送**する |
        | 上記以外の 4xx | 受け付けていない（`failed`） | 次の実行が新しい要求として作り直してよい |
        | 実行をまたいだ試行が3回 | `gaveup` | 自動では送らない（赤い実行で知らせる） |
        | retry key の有効期限（LINE は24時間。こちらは23時間で判定）切れ | `expired` | 自動では送らない。作り直すと二重通知になりうるため |

        - ⚠⚠ **未確定の送信を「本文を作り直して新しい retry key で」送ってはならない。** 実は届いていた場合に2通になる。
          本文と retry key は**送る前に**記録へ書いてあり、落ちた実行の後始末もその記録から再送する。
        - ⚠ **記録を読めない・書けない・サービスアカウントが無いときは送らない**（`exit 1`）。二重通知より赤い実行で気づかせる方を選んだ。
          ただし一時的な失敗（記録の読み取り・OAuth）は 2秒 → 5秒 あけて計3回試す。確保の書き込みで応答が失われたときは読み直し、
          自分の確保が入っていれば先へ進む（入っていなければ作り直す）。
        - 設定異常は日付・判定時刻ごとに1枠（`anomaly`）。その回で一度通知したら、同じ枠で後から別の異常が出ても載らない。
          代わりに、その日の通知が出ないことがありうる。Actions の失敗を見ること。
        - ⚠ **`concurrency:` をワークフローへ足してはならない。** 待機中の古い実行が取り消され、6時分・7時分の取りこぼしになる。
        - 同じ日・同じ判定時刻を `targetDate` 指定で手動実行しても、通知済みの枠は送られない（意図どおり）。
          指定した日は本文に「判定対象日：…（手動指定）」と出る。
        - ⚠ **未来日の `targetDate` で実送信はできない**（`exit 1`。dryRun だけ可）。打刻が無いので全施設が未打刻になり、その日の枠が前もって送信済みになって当日の通知が止まるため。
        - 再送する本文は、固定の見出し（`【穂乃味タイムカード】\n朝出勤未確認（`）で始まり5000文字以内のものだけ。外れたら `expired`。
        - 記録の `state`・枠の値・ノード自体（`slots` / `batches` を含む）が想定外の形なら送らずに `exit 1`（空とみなして送り直さない・緑で黙って終わらせない）。
        - ワークフローは `permissions: contents: read`（鍵を受け取るジョブの GITHUB_TOKEN を読み取りに絞る）と `timeout-minutes: 45`。
        - ⚠ **既知の制限: 判定時刻より前に手動で実送信すると、その日の枠が先に送信済みになる。**
          例えば 05:00 JST に `targetDate` 空欄で実行すると全施設が未打刻として届き、06:03 の定時判定はその枠を再送しない
          （まだ打刻していない施設も再通知されない）。先に届いた通知で情報は失われないが、定時の判定結果としては弱くなる。
          **当日の手動確認は dryRun で行うこと。** 時刻で拒否する仕組みは、外部スケジューラの正当な実行まで止めうるので入れていない。
        - 通知済みの施設がある状態で新しく未打刻の施設が出た場合は、**新しい施設だけ**を「ほか N 件は通知済みのため省略」付きで送る。
        - 本番の条件付き書き込みの確認は `workflow_dispatch` の **`selfTest=true`**（LINE は送らない。`/morningNotify/_selftest` だけを書く）。
        - 記録は日付ごとに増える（1日2ノード・数KB）。自動削除はしていない。
      - ⚠ **外部スケジューラ（cron-job.org 等）の設定はリポジトリ外にあり、Agent からは変更しない**（本書の禁止事項）。必要なら人間に依頼する。
  - 通知確認 LINE通知（`scripts/notify-check.js`、`.github/workflows/notify-check.yml`、手動 `workflow_dispatch` のみ）
  - 打刻修正申請 FCM Push通知（`scripts/fcm-check.js`、`.github/workflows/fcm-notify.yml`、JST 8–22時に30分間隔）
  - 写真アップロード通知（管理者向け。LINE: `api/line-notify.js` / Discord: `api/discord-notify.js`、いずれも Vercel）
- **移動距離申請**: 職員別ON/OFFの独立モジュール（2026-08 追加）。詳細は下記「移動距離申請」節。
- **打刻時の顔撮影**: スタッフ別ON/OFF（既定OFF）。心理的な不正抑止のみで、写真は保存も送信もしない（2026-09-12 追加）。詳細は下記「打刻時の顔撮影」節。
- **施設端末の持ち出し検知**: 施設の設定範囲外へ持ち出されたら管理者へLINE通知（2026-09-12 追加）。判定はサーバ側 `/devmon`、検知は専用アプリ `devicewatch/`。確定の主経路として外部スケジューラ（cron-job.org・1分間隔）からの `POST /api/device-report` `action:"sweep"` を**実装した**（2026-09-13）。`DEVICE_SWEEP_KEY` と cron-job.org のジョブは **2026-09-13 に登録済み**（cron が毎分発火していることを Vercel の runtime ログで実測。誤った鍵で 403 が返るので鍵も登録済み）。⚠ **ただし cron が送る本文が JSON として読めておらず、確定の主経路はまだ機能していない**（下記「本文が JSON でないときは 400 `bad_json` を返す」）。詳細は下記「施設端末の持ち出し検知」節。
