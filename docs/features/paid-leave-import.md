# 有給残日数CSVの一括登録 — 2026-10-12

管理者メニュー「CSV一括登録」の **③ 有給残日数CSV**。移行時に、紙・Excel で管理していた有給の残日数をまとめて登録する。**全社共通**（会社ごとの分岐なし）。
コード: `index.html` の `CSVIMP`（純粋関数 `plSchedule` `validatePaidLeave` `buildPaidLeavePatch`）と `csvImpPlLoad` `csvImpPlCommit` `csvImpPlBodyHtml`。
回帰テスト: `node scripts/test-paid-leave-import.js`（依存なし・送信なし・合成データのみ）。関係する既存テスト: `test-csv-import.js` / `test-paid-leave-grant-edit.js` / `test-paid-leave-history.js`。

## CSV の列（見出しは必須。値は「氏名」「有給残日数」以外は空欄可）

| 列 | 意味 |
|---|---|
| 社員番号 | 空欄可。入れた場合はスタッフ管理の社員番号と一致しなければエラー（別人の取り違え防止） |
| 氏名 | スタッフ管理の氏名（姓＋名、空白なし）と**完全一致だけ**で本人を特定する。表記ゆれは推測で紐付けない |
| 有給残日数 | 0〜40、0.5日刻み |
| 年間出勤日数 | 付与日数の算出に使う（`judgeWeeklyEquivByAnnualDays` で週相当→`calculatePaidLeaveGrantDays`）。空欄ならスタッフ管理の週所定労働日数 |
| 直近付与日数・前回付与日数 | 入れた場合はこの値を付与日数にする（算出より優先） |

## 登録のしかた（★変えてはならない）

- 付与日・期限は**入社日から算出**（`calcPaidLeaveSchedule` と同じ式。テストで一致を検査）。期限内（期限 ≧ 今日 JST）の付与回を**全部**登録する（最大2回＝直近と前回）。
  登録しないと「付与予定（未登録）」に残り、そこから登録すると残日数が二重になるため。期限切れの古い付与回は登録しない（残日数に数えないので影響しない）。
- Excel の残日数は**直近の付与分の残り**として入れる。直近の付与日数を超える分だけを前回の付与分の残りへ入れる（古い付与から消化する FIFO と同じ考え方。合計は Excel の値のまま）。
  直近＋前回の付与日数を超える、期限内の付与が1回だけで付与日数を超える、はエラー（登録しない）。
- 付与行は `{id, staffId(社員番号), staffName, grantNum, grantDate, expiresAt, grantedDays, usedDays:0, remainDays, createdAt, source:"csvImport"}`。
  ★ **`remainDays` が正本**。`grantedDays − usedDays` で作らない（`grantedDays − remainDays` が登録時点の消化済み＝carryIn になる。`business-data-notes.md`）。
- 登録しない人（理由を画面に出す）: スタッフ未登録・表記ゆれ・同名が複数・退職・**社員番号なし**・社員番号の重複・**入社日なし**・付与前なのに残がある・付与日数を決められない・CSV内の同名。
- ★ **二重登録の防止**: その人の付与行が1件でもあれば（旧形式の `staffId=氏名` を含む）スキップする。同じCSVを2回取り込んでも2回目は全員スキップ。
- ★ 書き込みは従業員CSVと同じ流れ: ファイル選択時に最新のスタッフ・付与行を取得して検証 → 「登録する」で**登録直前に取り直して再検証**（確認時と内容が違えば書かずに確認し直させる）→ `tc5_paid_leave_balances` へ**1回の PATCH**（全部成功か全部失敗）→ 取り直して確認。取得できなければ書かない。
- 経路は既存の管理画面と同じ（`authFetch` → RTDB。権限は Rules）。新しい API・Rules 変更は無い。`csvImpCanWrite()` のときだけ登録できる。
- 付与通知（`tc5_staff_notifications`）は作らない（移行時の一括登録で、新たな付与ではないため）。

## 既知の制限

- 前回付与の日数も、CSV の年間出勤日数（直近の判定期間の実績）から算出する（前回の判定期間の実績とは限らない。プレビューに注記を出す）。違う場合は「前回付与日数」の列に入れる。
- 比例付与の第1回（入社6か月）の判定は本来「6か月の出勤日数×2」だが、CSV の年間出勤日数をそのまま使う。必要なら「直近付与日数」の列に入れる。
- 残日数は**取り込む日時点（直近の付与を含む）**の値を入れる。直近の付与日より前の時点の値を入れると、前回と直近の分け方がずれる。
- 一覧（有給残日数管理・付与日数修正）の「第N回」は既存の表示仕様で**登録済みの行の通し番号**であり、保存した `grantNum` ではない。CSVで直近・前回だけを登録した人は「第1回・第2回」と表示される（プレビューに注記）。
- 期限切れの古い付与回は「付与予定（未登録）」に残る。**登録しない**（残日数には数えないが、登録すると本人に付与通知が飛び、通し番号も付け替わる）。
- このシステムで既に承認した有給申請（付与行が無いまま承認されたもの）は、CSV取込では見ない。Excel の残日数がその分を引いているか、取り込み前に確認する。
- 登録直前の再取得から PATCH までのごく短い間に、別の管理者が同じ人の付与行を登録すると二重になりうる（従業員CSVと同じ設計上の制限）。
- 二重登録の判定は、生の `staffId`／`staffName` に加えて `normalizePaidLeaveBalance` で解決した社員番号でも行う（改名前の旧形式の行を検出する）。付与日数の列に入れられるのは 1〜20。

## 期限切れの未登録をまとめて消化済みにする — 2026-10-12

有給管理タブ「付与予定（未登録）」の上のボタン「期限切れの未登録 N件（M名）をまとめて消化済みにする」。
移行時、入社日から算出した古い付与回（期限切れ）が未登録のまま大量に残るため、1件ずつ「消化済み」を押す代わりにまとめて登録する。
コード: `index.html` の `PL-BULK-CONSUME-BEGIN/END`（`plBulkConsumeTargets` `plBulkConsumePatch`）と `plBulkConsumeBarHtml` `plBulkConsumeExpired`。テストは `test-paid-leave-import.js`。

- ★ **対象は期限切れ（期限 < 今日 JST）の回だけ。期限内の回は対象外**（消化済みにすると残日数0で確定し、取り込むはずの残日数が失われる。期限内の回は1件ずつの「付与登録」か有給残日数CSVで登録する）。
- 行の形は1件ずつの「消化済み」と同じ: `grantedDays`＝自動算出→手動週所定→不明なら0、`usedDays=grantedDays`、`remainDays=0`、`source:"bulkConsumed"`。期限切れなので残日数の合計・FIFO の消化対象に入らない。
- 登録直前に `tc5_staff`・`tc5_paid_leave_balances` を取り直し、同じ社員番号・付与日の行がある回、退職・社員番号が変わったスタッフの回は書かない。書き込みは1回の PATCH。取得できなければ書かない。付与通知は作らない。
