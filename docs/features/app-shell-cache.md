## index.html（app shell）の Cache Storage キャッシュ（2026-08-28）

**再訪問のたびに index.html（gzip 約231KB）を丸ごと再ダウンロードしていたのをやめた。**

### 変更前の問題（実測）

`sw.js` の navigate ハンドラが `fetch(new Request(req,{cache:'no-store'}))` で
**毎回 HTTP キャッシュをバイパス**していたため、リロードのたびに 236,171 B を取得していた。
GitHub Pages は `ETag: W/"…"` と `Cache-Control: max-age=600` を返しているが、この方式では活きない。

### 変更後の方式（stale-while-revalidate）

1. ナビゲーションは **Cache Storage から即座に返す**（ネットワーク転送 0）。
2. 裏で **HEAD** により配信中の `ETag`（無ければ `Last-Modified`）を確認する。
3. 変わっていたら本体を GET してキャッシュを入れ替え、`postMessage({type:'APP_UPDATE_AVAILABLE', version})` で画面へ通知する
   （`version`＝入れ直した版。2026-09-27 に追加）。
4. 画面は**安全な状態を待って1回だけ自動で再読み込みする**（2026-09-27 から。下記「自動更新」）。
   ~~既存の更新バナーを出し、自動リロードはしない~~ は廃止した。バナーは自動で更新できないときの予備としてだけ残る。

### 自動更新（APP-AUTO-UPDATE・2026-09-27）

`index.html` の `APP-AUTO-UPDATE-BEGIN`〜`END`。テストは `node scripts/test-app-auto-update.js`。

・**再読み込みの合図は SW の `APP_UPDATE_AVAILABLE` だけ**（＝新しい HTML をキャッシュへ入れ終えた後）。
　HEAD で配信版の変化を見つけた場合は、SW へ `CHECK_APP_UPDATE` を送って通知を待つ（最大20秒。来なければ
　SW 更新直後でキャッシュが空の場合なので、再読み込みでネットワークから取る）。SW が無い端末は HEAD の確認後に再読み込みする。
　★ 一定間隔で `location.reload()` する実装にしてはならない（入力を奪う・更新ループの原因）。
・**更新ループを起こさない**：再読み込みした版をタブの `sessionStorage`（`tc_app_autoreload`）に残し、
　**同じ版では二度と自動で再読み込みしない**（それでも古いままなら従来のバナーへ切り替える）。版の分からない通知（旧 SW）は
　10分に1回まで。記録を読み書きできない端末では自動で再読み込みしない。オフラインの間は再読み込みしない。
・**作業を失わせない**：`appReloadBlockReason()` が空になるまで待つ（2秒ごとに再確認し、最後の操作から5秒も待つ）。待つのは
　書込み通信の途中（`_appWritesInFlight`＝先頭で `fetch` に差し込んだ PUT/PATCH/POST/DELETE の件数）、`savingCount`、
　管理者の時刻修正＋承認の同時保存（`_apvBusyCount`・未確認・後回し・全体PUT送信中）、打刻の端末保存（`_punchSaving`）、
　PIN の入力・照合中、時刻セルの入力欄、移動距離・持ち出し検知・月別出勤日数の入力中、画面全体を覆うモーダル
　（修正理由の選択・確認など）、入力欄へのフォーカス、**表示されている**入力欄のうち初期値から変わったもの
　（閉じて `display:none` で残るモーダルの値は数えない。数えると自動更新が永久に止まる）。判定で例外が出たら再読み込みしない。
・**画面ごとの扱い**（`_appReloadScreenState()`）：ホーム画面は操作が無ければ自動で更新する。
　管理者URL・閲覧用URLの画面は、再読み込みで開いているタブ・月・職員が初期に戻るため、**表示中は待ってバナーで知らせ、
　タブが裏へ回った（非表示の）ときに自動で更新する**。PIN でログインした管理者・職員の画面・打刻の途中・管理者デモは、
　再読み込みでログアウト（操作の途中を失う）するため自動では更新せず、**バナーで知らせる**（押せばすぐ更新、ホームへ戻れば自動で更新）。
・作業中の待ちが30分を超えたら、自動更新を待ちつつバナーでも知らせる（保存が返ってこない等で黙って古いまま残さない）。
・作業中かどうかの判定は画面の状態より先に行う（作業中はログイン中の画面でもバナーを出さない）。ログイン中の画面のバナーは
　「新しいバージョンがあります。ホームに戻ると自動で更新されます。」と出す。
・★ バナーの［再読み込み］も押した時点で `appReloadBlockReason()` を確かめる。保存中・入力中なら再読み込みせず
　「保存・確定・キャンセルのあとで、もう一度押してください」と案内し、ログイン中の画面は「再読み込みするとログアウトします」と
　確認してから再読み込みする（バナーを出したあとに保存・入力が始まっていることがある）。
・この仕組みが入る前の版を開いている端末は、最初の1回だけ従来のバナーで更新する必要がある（以後は自動）。

### 「新しいバージョンがあります」が繰り返し出た不具合（2026-09-30 修正・sw.js v16）

原因は2つあり、組み合わさって「頻繁に・毎回」出ていた（検証サーバ＋Chrome で再現済み）。

1. **打刻端末のホーム画面で自動更新が永久に止まっていた。** 職員が PIN で打刻画面へ進んでも
   `staffPinInput` は消えずに残り、`appReloadBlockReason()` が画面を問わず「PIN 入力中（`pin`）」を返していた。
   そのため誰かが1度打刻した後はホームでも自動更新されず、30分後に予備のバナー（「再読み込みしてください」）が出た。
   ［再読み込み］も「保存中または入力中」と案内するだけで更新されなかった。
   ★ **PIN の入力値は PIN 入力画面（`pin` / `staffPin` / `staffPinNew`）にいるときだけ数える。**
   画面に結び付かない状態変数を、画面を問わずに「作業中」の判定へ使ってはならない。
2. **push のたびに「新しい版」と判定していた。** GitHub Pages の ETag は「配信時刻の16進-サイズ」で、
   index.html を変えない push（文書だけの変更など）でも毎回変わる（2026-09-30 実測。HEAD と GET・エンコーディングの違いでは揺れない）。
   ★ **版＝index.html の内容の SHA-256**（SW がキャッシュへ入れるときに計算し `X-TC-Shell-Hash` ヘッダへ残す）。
   ETag は「本体を取り直すかどうか」の目安にだけ使い、HEAD の ETag はキャッシュ済み本体の ETag と比べる。
   内容が同じなら通知せず、キャッシュだけ入れ直す（次からは HEAD だけで済む）。ハッシュを計算できない環境だけ ETag を版として使う。
   ★ 画面の HEAD 確認で ETag の変化を見つけても、SW が `APP_UP_TO_DATE` を返したら再読み込みしない
   （期限後の予備の再読み込みを取り消し、以後はその ETag を基準にする）。
   ★ SW が `APP_UP_TO_DATE` を返すのは**最新と確認できたとき（`'same'`）だけ**。キャッシュが空（SW 更新の直後）・
   通信失敗・非200 など判定できないとき（`'unknown'`）は答えず、画面は従来どおり期限後に1回だけ再読み込みする
   （「取れない＝最新」と扱うと予備の再読み込みが消え、古い画面が残る）。
   ★ 同時に来た確認（タブ復帰で2本届く等）は実行中の1本にまとめる（`_revalidating`。本体を二重に取らない）。
   ★ 保存する app shell は本体を展開済みで持つため、`Content-Encoding` / `Content-Length` を写してはならない
   （Content-Type・ETag・Last-Modified・ハッシュだけを持たせる）。したがって配信側が今後セキュリティヘッダ（CSP 等）を
   返すようになっても、キャッシュから返す応答には載らない。その場合はここへ明示的に足すこと。
・PIN の照合中（`pinChecking` / `staffPinChecking`）は画面を問わず待つ。

・Service Worker 自身の更新（`sw.js` の変更・`controllerchange`）は、アプリの版の判定に使わない。アプリの版の切り替えは
　「新しい HTML をキャッシュへ入れ終えた通知（`APP_UPDATE_AVAILABLE`）→ 安全を待って1回だけ再読み込み」だけで行う。
・回帰テスト: `node scripts/test-app-auto-update.js` の [8]（本物の `sw.js` を動かして、同じ内容の配信・同じ版で通知しないことを固定）と [8b]。

### ローカル実測（GitHub Pages と同じヘッダを返す検証サーバ）

| | 変更前 | 変更後 |
|---|--:|--:|
| 初回訪問の index.html 転送 | 236,171 B | 240,795 B ×2（プリフェッチぶん）＝ 481,590 B |
| **2回目以降の index.html 転送** | **236,171 B** | **0 B**（`deliveryType: "cache-storage"`） |
| 2回目の `domInteractive` | 108 ms | **56 ms** |
| 2回目の `loadEventEnd` | 594 ms | **109 ms** |
| 2回目のサーバ側リクエスト | GET 236,171 B | HEAD ×2（0 B）＋ `sw.js` 304 |

初回だけ二重取得になるのは、**Chromium ではナビゲーションの応答を Service Worker の `fetch` から
HTTP キャッシュ経由で再利用できない**ため（`default` / `force-cache` のいずれでもネットワークへ行くことを実測で確認）。
**2回訪問した時点で合計転送量はプリフェッチしない場合と同じ**になり、初回直後からオフライン起動できる利点が残る。

### 「速くなったが最新版に更新されない」を防いでいる仕組み

★ **`_appVersionTag` の HEAD 監視だけでは不十分になった。**
起動時に HEAD で取る ETag は常に「配信中の最新版」であり、**いま動いている HTML の版とは限らない**
（Cache Storage から古い版を返している可能性がある）。
そのため「古い HTML を実行中」を検知できるのは **Service Worker だけ**であり、
`_swSaysStale` フラグ（SW からの `APP_UPDATE_AVAILABLE` を受けて立つ）が唯一の経路になる。
**このフラグと `checkAppVersion()` の先頭の判定を外してはならない。**

多重の安全弁:

・**ナビゲーションのたびに HEAD で版を確認する**（1リクエスト・0バイト）
・オンライン復帰・タブ復帰で `CHECK_APP_UPDATE` を SW へ送る
・**版が取得できないときは必ず本体を GET する**（「取れない＝更新なし」と扱わない）
・`sw.js` の `CACHE_NAME` を上げれば `activate` で旧キャッシュを全削除する（最後の安全弁）

### 通知の取りこぼし対策（`__served_version`）

キャッシュを入れ替えたあとに再確認しても、比較相手がキャッシュ（すでに新版）だと差が無いことになる。
そのため **「最後に画面へ返した版」を Cache Storage の `\`/timecard/__served_version\`` へ残し**、
`CHECK_APP_UPDATE` ではそちらと比べる。これが無いと、postMessage を取りこぼしたタブは
**二度と更新に気づけない**（打刻端末は開きっぱなしなので1セッション＝数日になりうる）。
保存するのは版の文字列（内容のハッシュ。計算できない環境では ETag）だけで、個人情報は含まない。

★ **ETag の弱い印（`W/`）は比較前に外す**（`normVersion`）。
GitHub Pages は同じ内容でも `Accept-Encoding` によって印が付き外れする
（2026-08-28 実測: gzip なら `W/"6a9102ae-d926d"`、identity なら `"6a9102ae-d926d"`）。
**HEAD と GET の ETag は同じ `Accept-Encoding` なら一致することを実測済み**。

★ **HEAD が `!ok` のときは必ず本体を GET して確かめる**。405 を返す中継プロキシのある経路で
「何もしない」とすると、その端末は二度と更新に気づけない。

### 「後で」を無効化しない（予備のバナーが出たときだけの話）

★ Service Worker は**ナビゲーションのたび・画面復帰のたび**に通知しうる。
そのため `_appUpdateDismissedAt` を見て、「後で」を押してから 5分は再表示しない。
`checkAppVersion()` の `_swSaysStale` 判定も**間隔ゲートのあと**に置く。
この2箇所のどちらかをゲートの前へ戻すと、打刻端末では画面復帰のたびにバナーが戻り、
実質「後で」が効かなくなる（実機で確認済み）。

### キャッシュしてよいもの／絶対にしないもの

★ **Cache Storage へ入れるのは配信物だけである。**
`cache.put` を呼ぶのは app shell の1箇所だけ、`cache.addAll` は `OFFLINE_URLS` の1箇所だけ、という
**ホワイトリスト方式**にしてある（除外リスト方式にすると、新しい API を足したときに黙って漏れる）。

・Firebase Realtime Database（勤怠データ）・Identity Toolkit / securetoken（認証）・
　`timecard-rho.vercel.app/api/*`（通知・移動距離）は **一切キャッシュしない**
・`OFFLINE_URLS` は同一オリジンの静的アセットのみ（`manifest.json` とアイコン3種）。**HTML を入れない**
・**キャッシュキーは `/timecard/` に正規化する**。`?admin=` / `?token=` / `?demo=` などのクエリは
　キーに含めない（トークンがキャッシュに残らない／クエリごとにエントリが増殖しない）。
　権限判定は従来どおり実行時に `location.search` で行うため、正規化しても挙動は変わらない
・`manual.html` など app shell 以外のナビゲーションは**素通し**する（index.html を返してはならない）
・`ok` でない応答（404・エラーHTML）は保存しない

### 打刻データとの責務分離

打刻の端末保存は **IndexedDB（`timecard_punch_outbox`）** のままで、Cache Storage とは無関係。
`sw.js` は打刻データに一切触れない。

### 変更時の注意

★ **`sw.js` を変更したら必ず `CACHE_NAME` を上げる**（`timecard-vN`）。
これが「配信済みの古い app shell を確実に捨てる」唯一の安全弁になる。

### 既知の制限（未解消・運用で認識しておくこと）

1. **管理画面のセッション合計の転送量は減っていない。**
   承認漏れバナーは全タブ共通のヘッダにあるため、`ensureRecordsHistory()` はタブに関係なく走る。
   入口で待たされる量は 1,038,792B → 230,245B になったが、開いたままにすれば合計はほぼ同じ。
   ★ 2026-09-09 に**完了までの時間**は 14.3秒 → 2.5秒（シミュレーション実測）へ短縮したが、
   **転送量そのものは変えていない**（上記「通信量は減っていない（減らせなかった理由）」）。
   ★ これを減らすには「承認漏れの対象期間を限る」という**業務判断**か、
   Vercel 側の集計 API の追加が要る。推測で変えてはならない。
2. **月別出勤日数タブは選択年を1リクエストで取る。** 現在は5か月分だが、
   12か月分になると約2.8MB の単一リクエストへ成長する。その時点で月単位分割へ変えること。
3. **`tc5_approvals` は10秒ポーリングで毎回全件（54,471B）取得している**（今回の対象外）。
   現在のポーリング転送量の約56%を占める最大の残存コスト。
   ★ **読み取りだけを月に絞ってはならない。** `saveApprovals()` がノード全体 PUT なので、
   読みだけ絞ると承認1件で**他月の承認が全消滅する**。順序は必ず
   ①`saveApprovals` を per-key 書き込みへ → ②読み取りを月範囲へ。
4. **分割取得のあいだ、月ごとに `records` 全件を localStorage へ書き戻す**（月数回）。
   実測 6.4ms/回（デスクトップ・4,267件）。低速端末では体感しうる。
5. **打刻件数が現在の約4〜5倍（約5MB）で localStorage のクォータに達する**。
   `_lsSet` は無言で失敗するため、その時点で端末キャッシュの保持方式を見直すこと。
6. **初回訪問だけ index.html を二重取得する**（上記の実測表）。2回訪問した時点で相殺される。

### テスト

`node scripts/test-records-range.js`（依存パッケージなし・送信なし・本番データ非アクセス）。
期間取得と app shell キャッシュの両方を固定している。
全期間スキャンについては「同時取得が `HISTORY_CONCURRENCY` を超えない」
「背景の同時取得は変更前（1本）を超えない」「新しい月から順に発行する」
「完了のたびに次の月へ連鎖する（見張りタイマーを待たない）」「表示用の取得が飛行中なら始めない」
「表示用が停滞したら過去分を再開する」「取得失敗を連鎖で撃ち続けない」
「過去分がハングしても停滞した月そのものを取り直せる／その間は確定しない」
「背景が取得中の月を表示用が二重に取りに行かない／単日要求は待たせない」
「追い越された古い応答が新しいデータを巻き戻さない」を固定する。

承認漏れ・打刻漏れの**判定結果**は `node scripts/test-unapproved-summary.js` が固定する。
**`tc5_records` の取得範囲・管理画面の入口・月/年セレクタ・`sw.js` に関係する変更では実行必須**
（全件 PASS / 0 FAIL でなければ出荷しない）。テスト件数は増減するため固定値を規範にしない。
