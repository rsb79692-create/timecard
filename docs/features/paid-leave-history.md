## 有給取得履歴（管理者画面・2026-08-30）

管理者画面「有給管理」→ 有給残日数管理の職員行「▼ 詳細表示」を開くと、付与明細の下に
**「有給取得履歴」**が出る。職員ごとに「いつ有給を取得したか」を過去分まで追える。

### 正本と抽出条件（新しいデータは作らない）

・**正本は `tc5_paid_leave_requests` のみ。履歴用のデータを二重保存しない。**
　新しい Firebase パス（`tc5_paid_leave_history` 等）は作っていない。表示のたびに組み立てる。
・抽出は `index.html` の `// ===== PL-HISTORY-BEGIN/END =====` ブロックの
　**純関数 `plBuildLeaveHistory(requests, opts)`** が担う（DOM も通信も持たない）。
・突き合わせは **社員番号（`getReqStaffId`）が申請・付与行の両方にあるときは番号一致だけ**を採用する。
　どちらかが無い旧データのときだけ氏名でフォールバックする。
　★ 氏名だけで突き合わせると**同姓同名の取得履歴が混ざる**。この優先順を緩めてはならない。

### 実績と予定を分ける（★ここを変えると残日数と食い違う）

| 区分 | 条件 | 表示 |
|---|---|---|
| `taken`（有給取得履歴） | `status==="approved"` かつ 取得日 **≦ 今日（JST）** | 既定表示。取得日の降順 |
| `planned`（取得予定） | `status==="approved"` かつ 取得日 **> 今日（JST）** | 別枠・別ラベル。近い日から |
| `pending`（申請中） | `status==="pending"` | **別枠・別ラベル**。実績に混ぜない |
| `other` | `rejected` / `withdrawn` / `canceled` / **未知の status** | 既定は非表示。「取消・却下を表示」で開く |

★ **境界は `buildFutureApprovedLeaveMap`（残日数表示）と同じ「JSTで今日以前＝消化済み」**である
（`plTodayJst = getTodayJSTStr()`）。ここを変えると**画面の残日数と履歴の日数が食い違う**。
★ **pending を「取得済み」として出してはならない。**
★ **未知の status を黙って捨ててはならない**（データ異常を隠さない）。

### 複数日申請は取得日単位に展開する

1申請で複数日を申請できる（`leaveDates`）ため、履歴は**取得日1件＝1行**に展開する。
1日あたりの消化量は **1日固定**（承認時の FIFO 消化が `leaveDates.length` 日で行われるため）。
**半休は現行仕様に存在しない**（申請フォームに日数の入力欄が無い）。
取得日が無い異常データは**日数を推測せず無視する**。
1申請が過去日と未来日にまたがる場合は、日ごとに実績／予定へ振り分ける。

### 誤読させないための3点（★ここを外すと支給に直結する事故になる）

**1. 「実績 合計」は本システムで承認した分だけである。「付与日数 − 残日数」とは一致しない。**

`remainDays` には**運用開始前にすでに消化していた分（carryIn）**が織り込まれている
（付与登録モーダルが付与日数と別に残日数を入力できるため。本番実測で 40付与行中14行・最大10日）。
その分には申請データが無いので、**履歴には原理的に現れない**。
履歴セクションは付与明細（各行に「修正」ボタンがある）と同じカードに並ぶため、
「履歴が足りない＝残日数が誤っている」と読んで残日数を修正すると、**取得済みの有給が復活する**。
そのため見出しに「本システムで承認した分のみ」と明記し、`title` で理由を出している。
★ **この文言を外してはならない。** 履歴と残日数を一致させる方向の実装もしてはならない。

**2. 「取得予定」の日数はサマリー行の「残 N日（M）」の M と一致しないことがある。**

・履歴側 … 承認済みかつ明日以降の**取得日の実数**
・サマリー側 M … `buildFutureApprovedLeaveMap` が**付与行へ戻せる量で上限を切った値**
　（期限切れ・削除済みの付与行、`consumedSnapshot` 欠落では戻し先が確定せず M が小さくなる）

境界（JSTで今日以前＝消化済み）は同じで、違うのは上限クリップの有無だけである。
★ **どちらかに合わせて片方を書き換えてはならない。** 画面に注記を出して区別している。

**3. 改名すると付与行が旧氏名・新氏名の2グループに分裂する。履歴は2つ目以降を出さない。**

スタッフ改名（`index.html` のスタッフ管理）は `tc5_records` / `tc5_approvals` / `tc5_pins` を
付け替えるが、**`tc5_paid_leave_balances.staffName` と `tc5_paid_leave_requests.staffName` は
書き換えない**（既存挙動）。付与行のグループキーは氏名なので、改名後に新規付与すると分裂する。
一方 `normalizePaidLeaveBalance` は両方の `staffId` を同じ `employeeId` に解決するため、
社員番号で突き合わせる履歴は**両グループへ同じ全履歴と同じ合計日数**を出してしまい、
「2倍取得している」ように読める。
そのため `_plHistSidSeen` で社員番号を記録し、**2つ目以降のグループでは履歴を出さず参照先だけ示す**。
★ この抑止を外してはならない。

### 既存ロジックへは触っていない

`remainDays` の正本定義・`grantedDays`・`usedDays`・FIFO消化（`applyFifoConsumption` /
`reverseFifoConsumption`）・`buildFutureApprovedLeaveMap`・承認/却下/引戻処理は**未変更**。
履歴は完全に表示専用で、入力配列（`paidLeaveRequests` のキャッシュ）も書き換えない。

### 通信量（初回取得を増やしていない）

`paidLeaveRequests` は**有給管理タブへ入った時点で既に全件取得済み**（`selAdminTab("paidleave")`）。
履歴はそのメモリ上のデータから組み立てるだけで、**詳細を開いても追加の通信は発生しない**。
「さらに表示」「取消・却下を表示」も再描画するだけで通信しない
（`plHistMore` / `plHistToggleVoid` / `plToggleBalDetail` はいずれも `authFetch` を呼ばない）。
★ **履歴のために `tc5_records` や `tc5_paid_leave_*` の取得を増やしてはならない。**
管理画面の初回取得件数を削減した 2026-08-28 の変更を逆行させないこと。

### 表示（スマホ優先）

・**横長テーブルにしない。** 1件＝1〜2行の縦型（日付・日数・状態を1行目、申請/承認日時を2行目）。
・★ **履歴ブロックは付与明細の表の「外」に置く**（`overflow-x:auto` の閉じ `</div>` の直後、
　「新規付与を追加」の前）。付与明細を開くと表が `min-width:640px` になるため、表の中へ入れると
　スマホ幅で 640px の桁に引きずられて**右端の文字が切れる**。
　★ **`position:sticky` ＋ `width:calc(100vw - …)` で左端に固定する回避策を採ってはならない。**
　引き算する固定値がカードの実パディング・スクロールバー幅と連動せず、**320px 実測で文字が欠けた**。
　積み先は `plHistBlocks`、幅指定は `max-width:620px` だけにして、幅はカードに任せる。
・表の外へ出したぶん、見出しに氏名を出す（「有給取得履歴：〇〇」）。複数職員の詳細を同時に開いても
　どの職員の履歴か取り違えない。**この氏名表示を外してはならない。**
・既定は直近 **10件**（`PL_HIST_PAGE`）＋「さらに表示」で 10件ずつ追加。
・表示状態（`plHistLimit` / `plHistVoid` / `plBalDetailOpen`）は**メモリのみ。Firebase へ保存しない**。
