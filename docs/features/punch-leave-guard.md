# 承認済み有給の日の本人打刻禁止（2026-10-05）

> **この機能を変更・調査するときに必ず読む。** 常時守る要点は `AGENTS.md` にある。

有給申請が**承認済み（`status==="approved"`）**になった取得日は、本人の勤務打刻
（出勤・退勤・休憩開始・休憩終了・施設変更）を受け付けない。
申請中（`pending`）・却下（`rejected`）・取消（`canceled`）・引戻（`withdrawn`）・未知の status では従来どおり打刻できる。
連続有給（`leaveDates` の複数日）は対象日すべてが禁止。

実装は `index.html` の `// ===== PUNCH-LEAVE-GUARD-BEGIN/END =====` と `_execPunch`。

## 判定（別実装を作らない）

`punchLeaveApprovedOn()` は **`plBuildLeaveHistory()`（有給取得履歴）をそのまま使う**。
承認済みの判定・本人の突き合わせ（社員番号が両方にあれば番号一致だけ・無ければ氏名）・複数日の展開・
旧形式（`date` のみ）の扱いは履歴・残日数表示と同じになる。
★ **打刻用に有給の判定を書き直してはならない**（将来、履歴と打刻禁止の判定が食い違う）。

## どこで止めるか（★順序を変えない）

打刻はクライアントから RTDB `/tc5_records/{eventId}` へ直接 PUT する（サーバ API を通らない）。
RTDB ルールは `tc5_paid_leave_requests` を走査できず、ルールは honomi-board と共有で人の確認が要るため、
サーバ側での拒否はしない。加えて、サーバで拒否すると**端末に「打刻済み」で保存した打刻が送れなくなり、
端末とサーバが食い違う**。そのため止める位置は端末保存の直前に置く。

```
doPunch / openFacilityChangeModal … 先に案内（表示だけ。ここを外しても下で止まる）
_execPunch
  ⓪ punchLeaveWaitFresh()  … 本人向けデータの取得中なら最大 2 秒待つ（通信断では待たない）
     punchLeaveBlocked()    … 承認済みなら案内して return（端末にも records にも残さない）
  ① punchOutboxCommit()     … IndexedDB へ保存（従来どおり）
```

・打刻画面は承認済み有給の日に打刻ボタン（施設変更を含む）を無効化し、
　「この日は有給休暇が承認されているため、打刻できません。」を表示する（カメラの事前表示も出ない）。
・**画面の無効化は補助で、保存を止めるのは `_execPunch`**。古い画面のままボタンが押されても保存されない。
・`punchOutboxEnabled()` が偽（スタッフテスト画面・管理者デモ・閲覧用 URL）では判定しない（従来経路のまま）。

## データの鮮度（`// ===== PUNCH-LEAVE-FRESH-BEGIN/END =====`）

有給申請は `ensureStaffScopedData()` が PIN ログイン後（役割トークン確立後）に取得する。
施設端末は開いたままなので、**スタッフを選ぶたびに（`selStaff`）取り直す**（同じスタッフの再ログインでも古い承認で判定しない）。
★ **打刻画面にいる間は取り直さない。** 取得結果で配列を置き換えるため、送信中の有給申請・賄い確認を画面から消し、
　二重申請（承認されると残日数が二重に減る）につながる。時間経過での取り直しを足してはならない。

打刻の直前（`_execPunch` ⓪）に待つのは、**有給申請が未取得または最後の取得から 60 秒（`PL_FRESH_MS`）を過ぎていて、かつ取得中**のときだけ
（最大 2 秒 `PUNCH_LEAVE_WAIT_MS`、通信断では待たない）。有給申請は全スタッフ分を1つの配列で持つため、
直前に別のスタッフのログインで取得していれば待たない。待つ間はボタンを押せなくし「確認しています…」を出す。
取得中の印は世代つき（`plTrackFetch`）で、古い取得の完了が新しい取得の印を消さず、古い取得の結果で新しい結果を上書きしない。
有給申請ノードが空でも「取得成功」として扱う（取得失敗と区別する。空の会社で毎回待たせないため）。

この待ちは打刻の体感時間を延ばしうるが、「端末の古いデータのまま承認済み有給の日の打刻を作らない」要件
（整合性）のために置いている。待たない案（古い承認状態で判定）と、取得できるまで打刻させない案（オフライン打刻が止まる）は採らなかった。
PIN 入力より前に取得しておく案は、有給申請の読み取りに要る役割トークンが PIN 認証の後でしか確立しない（`afterElevation`）ため採れない。
★ 待つ間の「確認しています…」は画面下に重ねて出し、打刻ボタンと顔撮影の枠は消さない・動かさない
（枠を消すと顔撮影のプレビューが止まる。押しても `_punchSaving` で受け付けない）。

## 既知の制限（運用で認識しておくこと）

1. **有給申請を取得できていない状態（完全オフライン・役割トークン未確立・取得失敗・2 秒以内に取得が終わらない）では打刻を止めない。**
   オフライン打刻（端末保存→自動再送）を優先する設計で、取得できた最新の承認状態で判定する。
2. **承認より前に端末へ保存済みの打刻（未送信を含む）はそのまま送る。** 端末とサーバを食い違わせないため。
3. ログイン（スタッフ選択）より後に承認された分は、次にスタッフを選ぶまで反映されない。
   直前 60 秒以内に別のスタッフのログインで取得したデータは、そのまま使う（その間の承認は次の取得まで反映されない）。
4. 打刻日（`date`）は端末の日付（`fmtDateKey`）で判定する。日付をまたいだ退勤が有給日に当たる場合も止まる。
   出勤後（申請中の状態で出勤）にその日の有給が承認された場合も、退勤・休憩・施設変更は止まる
   （「出勤だけ止めて退勤等は通す」形にしない要件のため）。退勤の無い出勤は管理者が勤怠修正で直す。
5. **本ガードは誤操作の防止で、サーバ側では強制していない。** 改ざんしたクライアントや RTDB への直接書込みでは回避できる
   （`tc5_records` は匿名でも書ける起動面のため）。サーバ側で強制するには honomi-board と共有する RTDB ルールの変更と
   人の確認が必要で、起動面の `tc5_records` の扱い自体の見直しを伴う（`tc5_pins` の平文 PIN と同じ起動面の課題）。
   権限の昇格・他人のデータの閲覧は起きず、重なった場合は管理者の勤怠修正で処理する。
6. ログイン時の取り直しが失敗したとき（通信断・役割トークン期限切れ）は、直前に取得できた承認状態のまま判定する。
   その間に承認が取り消された場合、取り直せるまで打刻が止まることがある（管理者修正で回復できる）。

## 管理者操作・既存データ

・管理者の勤怠修正・追加（`saveRecord` / `patchRecord`）、承認・却下・引戻、有給管理はこの判定を通らない。
・既存の打刻データは変更しない。「承認済み有給＋同日の打刻」が既にあっても自動では直さない。
