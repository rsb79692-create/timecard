## 施設端末の持ち出し検知（2026-09-12）

施設に置いてある打刻用スマホが施設の設定範囲外へ持ち出されたとき、管理者へ LINE 通知を1回出す。

| 層 | 実装 | 役割 |
|---|---|---|
| 管理画面 | `index.html` の `// ===== DEVWATCH-BEGIN/END =====` | 監視ON/OFF・基準位置・許容半径・登録端末の表示だけ |
| 管理API | `api/device.js` | 管理者ロール専用。設定の読み書きと登録コードの発行 |
| 端末API | `api/device-report.js` | 監視アプリ専用（`register` / `report`）＋**定期実行の入口**（`sweep`） |
| 共通ロジック | `api/_lib/device.js` | 距離・継続判定・重複抑止・LINE本文・送信 |
| 監視アプリ | `devicewatch/`（Expo / iOS・Android） | 位置と権限状態を報告するだけ |
| 定期実行 | 外部スケジューラ（cron-job.org）→ `POST /api/device-report` `action:"sweep"` | **管理画面を開かなくても確定・通知させる主経路**。1分間隔 |

### 新しい管理画面は作っていない

既存「マスター管理」タブの「拠点トークン管理」の各施設行の中に、折りたたみで
「端末持ち出し監視」を足しただけである。★ **履歴画面・端末管理画面・設定画面を新設してはならない。**

### データの置き場所（★ここを動かしてはならない）

**RTDB のルート直下 `/devmon`。`database.rules.json` に未定義＝デフォルト拒否**で、
打刻端末・職員・労務士からは直接読み書きできない（`/mileage` と同じ方式）。

```
/devmon/_meta                  {createdAt, version}
/devmon/settings               {dwellSec, staleSec, defaultRadiusM}  ← UIは持たない。未設定なら既定値
/devmon/facilities/{fkey}      {name, lat, lng, radiusM, enabled, basedOn,
                                createdAt, updatedAt, updatedBy}
/devmon/enroll/{CODE}          {fkey, name, setBaseFromDevice, expiresAt, createdAt, createdBy}
                               ← 24時間で失効。期限切れは次の発行時にまとめて削除する
/devmon/devices/{deviceId}     {fkey, label, platform, tokenHash,
                                state, pendingSince, notifiedAt,
                                lastSeenAt, lastDistM, lastAccM,
                                lastJudgedAt, unjudgedNotifiedAt, staleNotifiedAt,
                                permState, permDetail, permNotifiedAt,
                                createdAt, createdAtMs, revoked, revokedAt, revokedBy}
```

★ `lastJudgedAt`（位置判定が成立した時刻）と `createdAtMs` は「判定できていない検知」の土台である。
消すと、位置を送らない端末が永久に正常扱いになる。`lastAccM` は管理画面の診断用。

★ **`/honomi` 配下や `master/locations` へ置いてはならない。** `/honomi` は打刻のために
`tc5_records` / `tc5_pins` / `master/locations` を匿名または一般スタッフへ開けてある。
そこへ監視設定を置くと、**監視対象の端末自身が「監視OFF」「基準位置＝自宅」「範囲内」と書けて、
検知そのものを無効化できる**（朝の未打刻判定の時刻を `master/locations` へ持たせないのと同じ理由）。

★ **施設の緯度・経度は既存データに存在しなかった**（`master/locations` は `{name, token}` の2キーのみ、
`/mileage/places` にも座標なし。2026-09-12 に実測）。二重管理ではなく新規に持たせている。
施設の対応づけは**施設名の正規化（NFKC＋空白除去）から導く16桁のキー**で行う。
施設マスタに改名機能が無い（改名＝削除＋追加）ため、**改名した施設は監視設定を作り直す必要がある。**

### 判定はすべてサーバ側にある

★ アプリは「位置と権限状態」を報告するだけで、持ち出し確定・重複抑止・通知の判断を持たない。
アプリを書き換えても判定を変えられないようにするため。**この分担を崩してはならない。**

★ **経過時間はサーバ受信時刻で測る。** 端末が申告した時刻（`at`）は判定に使わない
（端末時刻を進めるだけで「3分継続した」と偽れるため）。`evaluateReport` は `rep.at` を読まない。

★★ **ただし位置そのものは端末の自己申告である。** 判定をサーバへ置いた目的は
**重複通知の抑止と端末時刻の偽装対策**であって、**位置の真正性の保証ではない**。
改造クライアント・エミュレータ・OSの位置偽装で「範囲内」を偽ることはできる。
移動距離申請の `tc5_records` と同じ種類の残存リスクであり、「サーバで判定しているから安全」と
読み替えてはならない（2026-09-12 の監査で明記）。
代わりに**偽っても痕跡が残る**ようにしてある（位置を送らない・粗い測位だけを送る端末は
「位置を判定できていません」として通知される）。

| 判定 | 内容 |
|---|---|
| 範囲外 | `距離 − min(測位誤差, 100m) > 許容半径` |
| 持ち出し確定 | 最初に範囲外を受け取った時刻から **既定180秒**以上経過。**次の報告**か、サーバ側のスイープで確定する |
| 再通知 | しない。範囲内へ戻ると内部状態が戻り、次の持ち出しで再び通知する（復帰通知は出さない） |
| 粗い測位 | 誤差 300m 以上は判定に使わない。★ このとき**継続計測を消さない**（粗い測位を挟んで3分計測をリセットさせない） |
| 測位誤差の申告なし | 差し引き上限（100m）として扱い、**判定は行う**。★ 判定スキップにすると「`acc` を省略すれば検知されない」抜け道になる |
| 監視OFF・基準位置未設定 | 判定しない。推測で「範囲内」にもしない |
| 権限の喪失 | 「常に許可」でなくなったら1回だけ通知。「常に許可」へ戻ると再アーム（★ `permState` と **`permDetail` の両方**を消す。消さないと管理画面が永久に赤のままになる）。★ **通知は監視ONの施設だけ**。状態の記録は OFF でも行う（管理画面の表示を正確に保つため） |
| 受信途絶 | 既定24時間。1つの途絶につき1回だけ通知 |
| **位置を判定できていない** | 報告は届くが判定が成立しない状態が既定24時間続いたら通知。★ 下記 |

端末の状態（`/devmon/devices/*/state`）は4つ。**"inside" を既定値にしてはならない。**

| state | 意味 |
|---|---|
| `unknown` | 登録直後。位置を1度も判定していない（管理画面は「未判定」） |
| `inside` | 判定して範囲内 |
| `pending` | 判定して範囲外だが、まだ継続時間に達していない（管理画面は「範囲外を確認中」） |
| `outside` | 持ち出し確定・通知済み |

★ **「判定できていない」を正常として表示してはならない（フェイルクローズ）。**
位置を送らない・測位が粗すぎる報告は `lastSeenAt` だけを更新するので、受信途絶にはならない。
判定が成立した時刻（`lastJudgedAt`）を別に持ち、それが古い端末は
管理画面で赤く出し、しきい値を超えたら LINE で通知する。
これが無いと、**監視が死んでいるのに管理画面が緑（監視中）のまま**になり、
偽装（位置を送らない改造クライアント）も屋内の測位不良も検知できない。

★ **スイープが「端末が沈黙しても確定させる」経路である。** 範囲外を1回報告した直後に
電源を切る・機内モードにするのが持ち出し時の自然な行動であり、
次の報告を待つ設計だけでは**通知が永久に出ない**。経過はサーバ受信時刻で測っているので、
端末の追加報告は本来不要である。

スイープが走る契機は次の3つ。**判定の実装は `runSweep` だけ**で、二重実装は無い。

| # | 契機 | 位置づけ | 稼働状態（2026-09-13） |
|---|---|---|---|
| ① | 外部スケジューラ（cron-job.org）→ `POST /api/device-report` `action:"sweep"`（**1分間隔**） | **主経路**。管理画面を誰も開かなくても、範囲外3分で LINE が来るのはこれによる | 登録済み・**毎分発火している**（Vercel ログで実測）。⚠ ただし本文が JSON として読めておらず **400 `bad_json`** のため**未達**（2026-09-13） |
| ② | 端末の報告時（`SWEEP_MIN_INTERVAL_MS` で間引く） | 保険 | 稼働 |
| ③ | 管理画面を開いたとき（`/api/device` の `bootstrap`） | 保険 | 稼働 |

⚠ **①が登録されるまでは、下記「既知の制限1」の旧挙動（端末1台の施設では管理画面を開くまで
通知が出ないことがある）がそのまま残る。** 登録と初回の 200 応答を目視確認してから
「稼働」へ書き換えること（7時分の cron と同じ扱い。本書冒頭「確認できた事実のみ」に従う）。

★ **②③ を外してはならない。** ①はリポジトリ外の設定で、止まっても GitHub Actions のように
失敗が見えない（cron-job.org 側の実行履歴でしか気づけない）。朝の未打刻通知を
cron と外部スケジューラで二重化しているのと同じ考え方である。

★ **報告の機会に走らせるスイープは、1インスタンスあたり59秒に1回までへ間引く**
（`SWEEP_MIN_INTERVAL_MS`）。
★ **定期実行の間隔（60秒）の直下に置く。** 45秒だと「cron の直後15秒の窓」へ入った端末報告が
冗長な全件スイープを重ねる（実測: 7台で 720回/日・50台で 1,440回/日）。59秒なら窓が1秒に縮み、
同条件の実測で **0回/日**になる。cron 停止時も、端末の報告間隔120秒 ≥ 59秒なので保険は
全報告で走る（遅れは最大14秒増）。
★ 継続時間の最小値 `MIN_DWELL_SEC`＝60秒より必ず短く保つ。同値以上にすると、
dwell を最小へ下げたときに確定が最大2倍遅れる（`Math.min` の第2項がこれを構造的に保証する）。
毎報告で走らせると、1端末の評価のために毎回 `/devmon/facilities` と `/devmon/devices` を
全件読むことになる（端末50台で概算130MB/日。RTDB は打刻と共有している）。
しきい値は確定=180秒・途絶=24時間なので、60秒間隔で取りこぼしは生じない。
間引いた回は自施設1件だけを読む。
★ `/devmon/settings` は管理UIを持たず変更が極めて稀なので、**5分**だけウォームインスタンス内で
使い回す（`SETTINGS_TTL_MS`）。
★ **TTL は呼び出し間隔より必ず長くする。** 60秒にしていたが、定期実行が60秒間隔・端末報告が
120秒間隔なので**命中率が実測0%**で、キャッシュが一度も効いていなかった。
★ 無期限にしてはならない（設定変更が永久に反映されなくなる）。
★ キャッシュするのは `dwellSec` / `staleSec` だけである。**認可に関わる値
（端末トークン・`revoked`・施設の `enabled`/座標/半径・管理者ロール）は毎回新鮮に読む。**

### 定期実行（管理画面を開かなくても通知する）— 2026-09-13

`POST /api/device-report` に `action:"sweep"` を足した。**新しいエンドポイントは作っていない。**

```
POST https://timecard-rho.vercel.app/api/device-report
Content-Type: application/json
{"action":"sweep","key":"<DEVICE_SWEEP_KEY と同じ値>"}
```

★ **判定は `D.runSweep` をそのまま呼ぶだけ**で、この経路に独自の判定ロジックは無い
（`sweepPlan` / 距離計算 / LINE本文の生成をここへ書いてはならない）。

**なぜ別エンドポイントにしないか**

1. Vercel の Serverless Function は Hobby プランで **12本が上限**で、現在 **11本**ある。
   endpoint を1本増やすと上限に張り付き、次の機能追加で deploy そのものが落ちる。
2. 外部スケジューラは `Origin` を送らないため、`api/_lib/http.js` の `guard`（Origin 必須）は使えない。
   `api/device-report.js` の `guardApp`（Origin を見ない・CORS を返さない）がそのまま要件に合う。

**なぜ Vercel Cron を使わないか**

Hobby プランの Cron は **1日1回**しか実行できない（頻度を上げるには Pro が必要）。
GitHub Actions の `schedule` も、このリポジトリでは **1時間45分〜2時間22分遅れる**ことを実測している
（上記「朝出勤確認 LINE通知」の表）。1分間隔を満たせるのは外部スケジューラだけである。

**認証（★ 順序を入れ替えてはならない）**

```
① 共有鍵の照合（環境変数 DEVICE_SWEEP_KEY・定数時間比較・RTDB へ0往復）
② IP単位のレート制限（10分窓60回。鍵が漏れたときの上限）
③ 設定・施設・端末の取得 → runSweep
```

★ `sweep` だけ**鍵の照合をレート制限より前**に置いている。これは
「認証より前に重い取得をしない」という同ファイルの不変条件を**弱めるものではなく、より厳しい順序**である
（鍵を知らない相手は RTDB へ1往復も起こせない）。逆にレート制限を先に置くと、
鍵を知らない攻撃者のリクエストが `bumpAndCount` の2〜3往復へそのまま変換されてしまう。

★ 鍵は **32文字以上をコード側で強制する**（`SWEEP_KEY_MIN_LEN`）。鍵の誤りにはレート制限が
掛からないため、総当たりに耐えるのは鍵の長さだけである。**この値を下げてはならない。**
★ 鍵は**前後の空白と改行を無視して照合する**。環境変数やジョブ本文に改行が1文字混ざるだけで
恒久的に 403 になり、しかも 503（未設定）と区別できず切り分け不能になるため。
★ `DEVICE_SWEEP_KEY` が未設定・32文字未満のときは **503 `sweep_not_configured`** を返す。
黙って何もしない状態を作らないため（外部スケジューラの実行履歴に失敗として残る）。

★ 鍵は **`register` / `report` には一切効かない**。端末の認証は従来どおり端末トークンである。

**本文が JSON でないときは 400 `bad_json` を返す（★ 500 にしてはならない）— 2026-09-13**

⚠⚠ **Vercel の body パーサは `Content-Type: application/json` で解析に失敗すると、
`req.body` を参照した時点で例外を投げる。** これを handler の汎用 `catch` へ落とすと
**500 `server_error`** になり、「クライアントの本文が壊れている」ことが運用者から見えなくなる。

実際に起きた（2026-09-13）。外部スケジューラの本文が JSON でなかったため `action:"sweep"` が
**毎分 500** を返し続け、応答本文は `{"error":"server_error","cid":…}` だけで原因へ辿れなかった。
Vercel の runtime ログには `[device-report] <cid> Invalid JSON` が毎分1件出ていた。

対処は `readJsonBody` / `bodyFingerprint`（`api/device-report.js`）。

| 本文 | 応答 |
|---|---|
| 正しい JSON オブジェクト | 通常処理へ |
| 前後に空白／改行 | **受け付ける**（Vercel の `JSON.parse` 自体が JSON の空白を許すため、そもそも例外にならない） |
| BOM 付き | **400 `head=unread`**。★ 下記のとおり本番では `req.rawBody` が無いため回復できない |

⚠⚠ **本番の Vercel は `req.rawBody` を提供しない（2026-09-13 実測）。**
form 形式の本文を本番へ投げたときの応答は `{"error":"bad_json","hint":"len=~48-63 head=unread"}` で、
`head` が `word` ではなく `unread` だった。つまり**解析に失敗した本文の中身はサーバ側から見えない**。

したがって本番で得られる指紋は実質 **`len=~N-M head=unread` だけ**である。

・`head=brace` / `percent` / `word` / `quote` などの分類は、**`req.rawBody` を提供する実行環境
　（および回帰テスト）でのみ現れる**。本番の切り分けには使えない。
・代わりに**長さ**で切り分ける。本文の固定部分は既知なので、鍵の長さ `L` に対して
　　正しい JSON `{"action":"sweep","key":"…"}` … **27 + L** バイト
　　form 形式 `action=sweep&key=…` … **17 + L** バイト
　の差（10バイト）から判別できることが多い。
・★ **この差を埋めるために本文のストリームを自前で読む実装を足してはならない。**
　本文は handler 起動前にプラットフォームが消費しており、ハングの危険と引き換えに
　得られるのは診断情報だけである（400 を返すという本質的な挙動は既に正しい）。
　診断が必要なら、運用者に外部スケジューラの設定画面を確認してもらうのが確実で安全。
| form 形式（`action=sweep&key=…`）・URL エンコード・末尾カンマ等 | **400 `bad_json`** ＋ 指紋 |
| 本文なし・空 | 従来どおり 400 `bad_action` |

★ **本文の不正はクライアントエラーである。** 400 で返し、原因が分かる指紋を添える。
★ **直すのは BOM と前後の空白だけにする。** form 形式や URL エンコードを黙って受け付けると
入力形式を2つ持つことになり、`guardApp` の Content-Type 検査（415）が意味を失う。
★ 判定は **レート制限より前**に置く（壊れた本文で RTDB を1往復も叩かせない）。
従来も `req.body` の例外は `bumpAndCount` より前に起きていたので、露出は増えていない。

★★ **指紋（`hint`）に本文の内容を含めてはならない。** 本文には共有鍵と端末トークンが入るため、
先頭数文字でも出せば資格情報が漏れる。出してよいのは次だけである。

```
len=<バイト長> head=<brace|bracket|percent|quote|word|bom|other|empty|unread>[ form=1]
```

・`len` は Content-Length として経路上どこでも見える値なので、新たな露出にはならない
・`head` は**先頭1文字の分類**のみ。`form=1` は `=` の有無のみ
・`hint` は応答にも入れる。**呼び出し元が自分の送った本文について知るだけ**なので露出にならず、
　運用者が外部スケジューラの画面だけで自己診断できる（ログ閲覧が要らない）

★ `api/device.js` / `api/mileage.js` / `api/auth/*` も `req.body` を同じ形で読んでおり、
**同じ潜在欠陥がある**（不正な本文で 500 になる）。呼び出し元が自前の `index.html` なので
実害は出ていないが、共有の `api/_lib/http.js` の `guard` へ入れると全エンドポイントへ波及するため
今回は `device-report.js` に限った。未対応事項として記録している。

**コスト（1分間隔・スタブで往復数を実測。推測ではない）**

定常状態（ウォーム・通知なし）の1回あたり **RTDB 往復 5〜6回**

**設定（リポジトリ外。Agent からは変更しない）**

1. Vercel の環境変数 `DEVICE_SWEEP_KEY`（32文字以上のランダム文字列）を Production へ登録して再デプロイ
2. cron-job.org に「毎分・POST・上記の JSON」を登録

★ どちらもリポジトリ外なので、**本書の禁止事項どおり Agent からは設定しない**。人へ依頼する。

★ **端末アプリの報告間隔は 120秒**（`REPORT_THROTTLE_MS`）。これがレート制限に対する歯止めで、
最終報告時刻は端末へ**永続化**する（背景タスクは新しい JS コンテキストで起こされることがあり、
メモリだけで持つと 0 に戻って間引きが効かなくなる）。

★ `distanceInterval`（**位置更新で起こされる距離のしきい値。ジオフェンスの半径とは別物**）は **200m**。
・小さくすると起床が増える（電池のみ。報告回数は上の120秒で頭打ち）
・大きくすると、**施設の数百m先へ持ち出してそのまま置かれた場合に2回目の報告が発生せず**、
　確定がサーバ側スイープ（＝他端末の報告か管理画面の表示）だけに依存する
許容半径（既定150m）と同程度にして、検知の確実性を優先している。

★ ジオフェンスの出入りは間引かない（継続計測の開始時刻そのものなので落とせない）。
サーバの最短間隔（10秒）で弾かれた場合だけ、12秒待って1回やり直す。

★ **監視OFFでも端末側の監視を止めてはならない。** `report()` を呼ぶ自動契機は
ジオフェンスと位置更新の2つだけなので、止めると端末は新しい設定を取りに来る手段を失い、
**管理者が監視をONに戻してもアプリを開くまで再開しない**。OFF のあいだはサーバ側が判定・通知の対象から外す（位置の判定・持ち出し確定・受信途絶・
判定不能・**権限の通知**のすべて）。届いた報告で進むのは `lastSeenAt` と、権限状態の**記録**だけである。
アプリは起動・復帰時に監視が落ちていれば自分で張り直す（`ensureWatching`）。

★ **通知は「範囲外になってから3分後ちょうど」には来ない。** 「3分以上経ったあとの最初の報告」で出る。
移動中は位置更新が届くため通常は数分だが、**遅れることがある**。この性質を「3分で通知する」と
書き換えてはならない。

★ **通知の種類ごとに「取り逃し」と「重複」のどちらへ倒すかを決めてある。逆にしてはならない。**

| 通知 | 印を付ける順序 | 理由 |
|---|---|---|
| 持ち出し検知（exit） | **送信できてから**確定（`state:"outside"` / `notifiedAt`）を書く | 先に書くと、巻き戻しに失敗した時点で `evaluateReport` も `sweepPlan` も拾わなくなり、**その持ち出しのアラートが完全に失われる**。重複は許容し、取り逃しを避ける |
| 受信途絶・判定できていない | **印を先に付けてから**送る | Vercel は同時実行でスケールするため、送ってから印を付けると同時に走ったスイープが同じ集約通知を何通も出す。取り逃してもしきい値で再評価されるので、重複を避ける |

★ 同じ継続についての再確定は、前の持ち出しの通知（`notifiedAt`）が今の継続より新しいときだけ抑止する。
**同じ持ち出しで LINE を送れたのに確定の書き込みに失敗した場合は、スイープが再送する**
（＝重複しうる）。持ち出し検知は取り逃しより重複を選ぶ、という上の表の方針どおりである。
受信途絶・判定できていない側は逆で、印を先に付けるため重複しにくいが、
**再アームはしきい値ぶんの時間差で判定する**（印だけで抑止すると、印を戻せなかった時点で
二度と通知されなくなる）。
★ 継続開始より新しい位置判定が無い端末は確定させない（監視OFF・基準位置変更をまたいだ
古い観測で、現在位置を見ずに通知しないため）。

★ **基準位置・半径・ON/OFF を保存したときは、その施設の端末を次のように扱う。**
・`state` が `outside`（持ち出し確定済み）以外の**全端末**を `pendingSince:null` / `state:"unknown"` へ戻す。
　★ `pendingSince` を持つ端末だけでは足りない。旧基準で `inside` だった端末が
　「古い判定のまま緑（監視中）」で残る。
・`unjudgedNotifiedAt` を now にして**しきい値ぶんの猶予**を与える。
・`staleNotifiedAt` の猶予は「保存時点でまだ沈黙していない端末」だけに与える。
　★ `lastSeenAt` は監視OFFでも進むので、すでに沈黙している端末は**本物の異常**である。
　無条件に猶予すると、その通知を最大しきい値ぶん（計48時間）遅らせてしまう。
　★ 監視OFFのあいだ `lastJudgedAt` は進まないので、OFF が長引いたあと ON へ戻すと、
　その場のスイープが即座に「位置を判定できていません」を送ってしまう
　（ON にした本人が誤アラートを受ける）。

### 通知は既存の LINE 基盤を再利用する

★ **通知基盤を新設していない。** 既存の Messaging API push と同じ環境変数
（`LINE_CHANNEL_ACCESS_TOKEN` / `LINE_TO_ID`。`api/line-notify.js` と共通）を使う。

```
【施設端末 持ち出し検知】
ミュゲの泉
9/12 20:15
施設の設定範囲外へ移動しました。
```

施設名は本文へ入れる前に制御文字・改行・ゼロ幅・双方向制御を落とす。
落とさないと、施設名に改行を混ぜて**偽の行（例「範囲内へ戻りました」）を本文へ差し込める**。

★ **受信途絶と「位置を判定できていない」は1通へまとめる**（`buildDigest`）。
端末ごとに送ると端末数に比例して外部通信が増える（N+1）。
**持ち出し検知（exit）はまとめない**（どの施設かを即座に伝える必要があるため）。

### 端末の登録

1. 管理画面で監視ON（または基準位置だけ）を**保存**する
2. 「端末の登録コードを発行」（8桁・24時間・1台ぶん）
3. 施設のスマホで監視アプリにコードを入力 → 位置情報を「**常に許可**」
4. 基準位置が未設定なら、**発行時に指定していた場合だけ**登録した端末の現在地を基準位置にする
   （誤差100m超なら基準位置を設定せず、その旨を返す。★ 粗い位置で基準を決めない）

★ 端末トークンは**登録時に1度だけ返し、以後はハッシュで突き合わせる**（定数時間比較）。
管理APIは端末トークンもそのハッシュも返さない。

★ **登録コードは発行時の1回だけ表示する**（`bootstrap` でも返さない）。閉じたら再発行する
（未使用コードは20件まで。期限切れは次の発行時にまとめて掃除する）。

★ 管理画面の端末一覧には **最終受信・位置判定の時刻・直近の距離** を出す（1端末＝2段で表示する。
1行へ詰めると 320px 幅で要素が散り、「（できていません）」が別の端末の行に見える）。
「監視中（緑）」を名乗る条件に「直近に位置判定が成立していること」を必ず含める。
★ **基準位置・半径が欠けている施設は「監視ON（基準位置が未設定）」（赤）で出す。**
サーバの `facilityReady()` と同じ条件を鏡写する。欠けているとサーバは一切判定しないので、
「判定待ち（待てば直る）」に見せてはならない。
★ **1度も位置を判定していない端末、および判定をやり直す状態（`state:"unknown"`）の端末が
あるときは緑にしない**（「監視ON（判定待ち）」）。判定不能の通知しきい値は24時間なので、
これが無いと設置直後の1日だけ「常に許可」を取れていない端末が正常に見える。
基準位置・半径・ON/OFF を保存するとサーバが該当端末を `unknown` へ戻すため、
`lastJudgedAt` だけを見ていると「判定していないのに監視中（緑）」になる。
★ **権限の異常（赤）は「判定待ち」「範囲外を確認中」（橙）より先に出す。**
後ろへ置くと、原因の提示が最大24時間遅れる。
★ 孤立した監視設定と表記ゆれの衝突は**描画のたびに**作り直す。取得時だけに計算すると、
拠点を追加した直後に衝突警告が出ず、削除後も孤立警告が残る。

★ **`register` は登録コードの実在だけで通る。** 管理者が発行したコードなので設計上は問題ないが、
コードを外部へ渡すと第三者の端末を登録できる。コードは口頭・手渡しで扱うこと。

### 報告1回の処理順序（★ 入れ替えてはならない）

`/api/device-report` は Origin を見ない＝**誰でも無認証で叩ける**。RTDB は打刻と honomi-board と
同居しているため、無認証の段階で重い取得を許すと打刻＝賃金側へ負荷が波及する。

1. **IP単位のレート制限**（登録 20回/10分・報告 120回/10分）。認証より前に必ず通す唯一のゲート
2. 端末IDの形式検査 → **端末1件だけを取得**してトークンを定数時間比較（ここで初めて認証が成立）
3. 同一端末の連打は、**すでに読み込んだ `lastSeenAt` との差**で弾く（追加の往復を使わない）
4. 認証後に設定・施設・端末一覧を**並列で**取得し、判定・保存・通知・スイープを行う

★ レート制限のキーをリクエスト本文の `deviceId` だけにしてはならない。
攻撃者が毎回ランダムな `deviceId` を送るだけで上限を素通りできる。

### 端末APIを別エンドポイントにしている理由

ネイティブアプリは `Origin` ヘッダを送らないため、`api/_lib/http.js` の `guard`
（Origin 不在を拒否する）をそのまま使えない。`api/device-report.js` は代わりに次を守る。

・Cookie を一切使わない（＝CSRF が原理的に成立しない）
・**CORS 応答ヘッダを一切返さない** → ブラウザからのクロスオリジン呼び出しは
　`application/json` のプリフライトが失敗して届かない
・認証は端末トークン。**レート制限は登録・報告ともIP単位**（登録 20回/10分・報告 120回/10分）。
　同一端末の連打は、すでに読み込んだ `lastSeenAt` との差（10秒）で弾く
　★ レート制限のキーをリクエスト本文の `deviceId` にしてはならない（毎回変えれば素通りできる）

★ **この2つを1つのエンドポイントへまとめてはならない。** まとめると、
管理者操作の Origin 検査を外すか、アプリを弾くかのどちらかになる。

### 既知の制限（未解消・運用で認識しておくこと）

1. **範囲外になる前から沈黙している端末は検知できない**（電源を切ってから持ち出す等）。
   OSの機能を使う以上避けられない。
   ★ 一方、**範囲外を1回でも報告したあとに沈黙した場合は定期実行のスイープが確定させる**
   （端末が1台だけでも、管理画面を開かなくても通知される）。
   ⚠ **ただしこれは①が実際に通るようになってからである。** ①が 400 / 403 / 503 を返している間は、スイープが走るのは
   「他の端末が報告したとき」と「管理者がマスター管理タブを開いたとき」だけなので、
   **端末が1台しか無い施設では管理画面を開くまで通知が出ないことがある。**
2. **位置情報を切られた／アプリを削除された瞬間は検知できない。** アプリが次に起動・復帰した
   ときに権限の異常を報告する。それも無ければ受信途絶（既定24時間）または
   「位置を判定できていません」として現れる。
3. **定期実行（cron-job.org）の設定はリポジトリ外にある。** 止まっても GitHub Actions のように
   失敗が見えず、**cron-job.org 側の実行履歴（HTTP ステータス）でしか気づけない**。
   止まった場合は保険の②③（端末の報告時・管理画面を開いたとき）だけが残るため、
   端末1台の施設では確定が遅れる。
   ★ `DEVICE_SWEEP_KEY` を Vercel から消すと **503** を返して**確定の主経路が止まる**
   （保険の②③だけが残る）。環境変数を整理するときに消さないこと。
   ★ 定期実行の設定も環境変数も Agent からは変更しない（本書の禁止事項）。人へ依頼する。
4. **iOS は静止している端末への背景実行を保証しない。** 受信途絶のしきい値を24時間にしているのは
   このため。**短くすると毎日のように誤警報になる。**
5. **Android を Play ストアで公開する場合、背景位置の利用理由について Google の審査がある。**
   内部配布（内部テスト・APK 直接配布）なら審査は不要。**iOS の実機配布には Apple Developer Program が必要。**
6. **施設を改名すると監視設定が孤立する**（施設マスタに改名が無く、削除＋追加になるため）。
   拠点を削除したときは設定と端末を自動で無効化するが、**改名では引き継がれない。**
   ★ 孤立した設定は「拠点トークン管理」の**警告枠（拠点マスタに無い端末持ち出し監視の設定）**へ
   一覧表示し、そこから「監視を解除」できる。これが無いと、孤立した設定は画面のどこにも現れず、
   監視をOFFにも端末の解除にもできないまま通知が出続ける（**管理導線の喪失**）。
   施設マスタは一般スタッフでも書けるため、この状態は職員の操作でも作れる。**この警告枠を外してはならない。**
   ★ 施設名の正規化（NFKC＋空白除去）で同じキーへ寄る拠点（例「ハルイロ」と「ハル イロ」）も
   衝突として赤く警告する。放置すると同じ設定が2行に出て、片方の保存が他方を上書きする。
7. **1回の報告でレート制限カウンタのために RTDB へ2〜3往復する**（既存 `bumpAndCount` の仕様）。
   報告は端末あたり15分間隔程度なので許容している。
8. **集約通知は施設名だけを並べる。** 同一施設に複数端末があると、受信途絶・判定不能の
   集約で同じ行が並んで区別できない（例「・ミュゲの泉（24時間以上）」×2）。
   持ち出し検知の書式を保つため端末名は入れていない。台数が増えたら見直す。
9. **同時実行での重複通知を完全には防げない。** 受信途絶・判定不能は「印を先に付ける」ことで
   ほぼ防いでいるが、RTDB に compare-and-set が無いため理論上は残る。持ち出し検知は
   意図的に重複側へ倒している（上記の表）。
   ★ 定期実行が1分間隔になったため、**LINE は送れたのに確定の書き込み（`confirmPatch`）だけが
   失敗し続ける**場合、放置すると持ち出し検知が最短1分おきに再送される。
   **確定を送信前に書く形へ変えてはならない**（それは通知の恒久的な喪失を招く）ので、代わりに
   `runSweep` が **「この継続（`deviceId + "@" + pendingSince`）の LINE はこのインスタンスから
   既に送れている」** をメモリに記録し、送信を繰り返さず**書き込みのやり直しだけ**を行う。
   ・キーに `pendingSince` を含めるのが要点である。**別の持ち出しは必ず `pendingSince` が違う**ので、
   　復帰後の再持ち出しを取りこぼさない。抑止するのは「すでに管理者へ届いた同一内容」だけ。
   ・**送信が失敗したときは記録しない**（記録すると通知の取り逃しになる）。
   ・記録は**最大200件・TTL 1時間**（`EXIT_SENT_MAX` / `EXIT_SENT_TTL_MS`）。上限を超えたら
   　最古から落ちる。端末上限は50台なので、生きている継続が押し出されることは実運用で起きない。
   　TTL で必ず失効するので、この保険が通知を恒久的に飲み込むことはない
   　（＝確定の書き込みが1時間以上失敗し続ける場合は、同一継続で1時間に1回まで再送する）。
   ・これは保険であって正本ではない（インスタンスが入れ替われば失われる）。正本は RTDB の
   　`notifiedAt` のまま。したがって重複が完全に 0 になるわけではない。
   ・**報告の経路（`handleReport`）の exit 送信はこの記録を通らない。** そこで確定の書き込みが
   　失敗した継続は、次のスイープが1通だけ重複させる（その1通が記録を作るので毎分再送にはならない）。
   ★ **LINE の push 枠は朝の未打刻通知（`scripts/morning-check.js`）と同じ資格情報・同じ枠である。**
   枠を食い潰すと業務上より重い通知まで沈黙するため、cron-job.org の実行履歴を監視すること
   （コード側の上限だけに頼らない）。見るべき値は次のとおり。
   ・**`stales` / `unjudged` が毎回 0 より大きいまま**続いていないか
   　★ **`sent` では検知できない。** LINE 自体が落ちている場合 `sent` は 0 のままで、
   　裏では送信試行と RTDB 書き込みが回り続ける（実測 2,880試行・5,760書込/日）。
   ・HTTP ステータスが 200 以外（403＝鍵違い／503＝未設定／500＝サーバ側の失敗）
   ★ 集約通知（受信途絶・判定できていない）側のこのループには `_exitSent` の抑止が効かない
   （抑止は持ち出し検知だけ）。安全側（取り逃し防止）を優先した結果であり、是正しない。
   ★ `sweepPlan` は形式が不正な端末ID（`isDeviceId` を満たさないキー）を対象にしない。
   `patchDevice` が必ず throw するため、1件混ざると「送れるが確定は永久に書けない」＝
   毎分の再送が**決定論的に**成立する。`markDevices` と対称に保つこと。
10. **登録コードは「発行時点で基準位置が未設定」のときだけ端末の現在地を基準位置にする。**
   発行後に管理者が手入力した基準位置を、古いコードでの登録が上書きすることはない
   （`base_already_set` を返す）。端末が基準位置を書いた場合は `updatedBy` に `device:<id>` を残す。
11. ⚠ **Vercel の Serverless Function が 11 本になった**（`api/` 配下の `.js`。直下5本＋`api/auth/`6本。2026-09-12 時点）。
   Hobby プランの上限は 12 本である。**次にエンドポイントを増やすときは、プランの実際の上限を
   確認してから足すこと。** 上限を超えると deploy そのものが失敗する。

### 専用アプリ（`devicewatch/`）

★ **勤怠アプリ全体をネイティブ化していない。** 持ち出し監視だけの1画面アプリで、
打刻・勤怠一覧・スタッフ一覧・履歴画面を持たない。個人データを扱わない。

★ **`package.json` を置いていない。** 依存の版は `npx expo install` が SDK に合わせて決める。
版を固定すると SDK と不整合な版が入り、ビルドが通らない／背景位置が動かない。
手順は `devicewatch/README.md` を正とする。

★ `App.js` は **JSX を使わず `React.createElement`** で書いてある。ビルド環境が無い本リポジトリでも
`node --check` で構文検査できるようにするため。**JSX へ書き換えてはならない**（検査手段が消える）。
⚠ ただし `import` を含むため、`node --check` が通るのは **Node 22.7 以降**（ESM 構文の自動検出）である。
GitHub Actions の `node-version: "20"` では `SyntaxError` になる。CI で検査対象にしていないので
現状は問題ないが、**ワークフローへ追加するなら Node のバージョンを上げること。**

⚠ **GitHub Pages はリポジトリ直下を丸ごと配信するため、`devicewatch/` のソースは公開される。**
資格情報を置いてはならない（現在はAPIのURLだけで、`index.html` が既に公開している値と同じ）。
Vercel へは配信しない（`.vercelignore` で除外済み）。

### テスト

`node scripts/test-device-watch.js`（依存パッケージなし・送信なし・本番データ非アクセス。I/O 関数は呼ばない）。
**持ち出し検知・`/devmon`・`api/device*.js`・管理画面の監視UIに関係する変更では実行必須**
（全件 PASS / 0 FAIL でなければ出荷しない）。テスト件数は増減するため固定値を規範にしない。
距離計算・継続判定・重複抑止・GPS誤差（`acc` 省略の抜け道を含む）・サーバ時刻での計測・
監視OFF時のフェイルクローズ・権限喪失の1回通知・受信途絶の1回通知・
**端末が沈黙してもスイープで確定すること**・**位置を判定できていない状態の検知**・
LINE本文（改行注入と集約）・権限マトリクス・`/devmon` がクライアントから到達不能であること・
端末APIが業務データを読まないこと・**認証より前に重い取得をしないこと**を固定する。

★ 定期実行については、1分間隔のスイープを**実際に回して**
「端末が沈黙していても3分で確定すること」「同一持ち出し中は1440回回しても通知が1回だけであること」
「3分未満で範囲内へ戻った外出は何回回しても通知しないこと」「復帰後の再持ち出しで再通知すること」
「再外出は今回の時刻から3分を測ること」「監視OFF・基準位置未設定では確定しないこと」を固定する。
入口については `sweepKeyError` を抽出して**値で**固定する（鍵なし・空・前方一致・非文字列・
超長文字列を拒否すること／未設定なら503／定数時間比較／鍵を応答とログへ出さないこと）、
および「鍵の照合がレート制限より前にあること」「`runSweep` へ委譲していて独自判定を持たないこと」
「保険の②③を外していないこと」「鍵は32文字以上を強制すること」
「振り分けに catch-all の else が無いこと（4つ目の action が鍵照合を通らずスイープへ落ちない）」
「定期実行は間引きの対象にしないこと」を固定する。

★★ さらに `POST /api/device-report` の **handler を実際に動かして**固定する。
そのために、テストの冒頭で `api/_lib/google.js`（RTDB・OAuth・外部HTTP）を require キャッシュで
スタブへ差し替えている。**この差し替えは `api/_lib/*.js` を require する前に行うこと**（後では効かない）。
狙いは2つある。

1. ソース走査と純粋関数だけでは、**結線の壊れ**（`guardApp` / action の振り分け / 応答の形 /
   鍵照合の位置）を検出できない。特に「管理画面を開かずに LINE が1通出ること」は
   handler を動かさないと確認できない。
2. 本ファイルの契約「送信なし・本番データ非アクセス」を**仕組みで保証する**。
   実装が誤って I/O を呼んでも、本番やLINEへ出る前にスタブで止まる。

handler で固定するのは、`guardApp`（GET=405 / 非JSON=415 / OPTIONS=403 / CORS 非返却 / `no-store`）、
**鍵が未設定・誤りのときに RTDB へ1往復も起こさないこと**、応答が件数だけであること、
**沈黙した端末を管理画面を開かずに確定させて LINE を1通送ること**、同一持ち出し中は何回叩いても
送らないこと、**確定の書き込みだけが失敗しても毎分送り直さないこと**（かつ書き込みのやり直しはすること）、
**送信が失敗した持ち出しは次のスイープで必ず送り直すこと**（取り逃さない）、
別の持ち出し（`pendingSince` が違う）は抑止しないこと、
監視OFF・基準位置未設定では確定しないこと、`sweep` の鍵で `register` / `report` が通らないこと。

★ 書き込みと LINE を意図的に失敗させる区間があるため、その区間だけ `console.error` を黙らせている
（実装のログ出力は変えていない）。区間を抜けたら必ず戻すこと。

★ 加えて、`index.html` の `DEVWATCH` ブロックを**実際に動かして**
「取得に失敗しても再取得を撃ち続けない」「プロトタイプを触る施設名で壊れない」
「孤立設定と表記ゆれ衝突を拾う」「判定できていない端末を『監視中』と表示しない」
「入力中は再描画で止める」を固定する。ソース走査だけにすると、これらの回帰を検出できない。
