## 打刻の端末永続保存と自動再送（2026-08-26）

打刻は**押した瞬間に端末（IndexedDB）へ保存し、その保存成功を確認してから**画面を「打刻済み」にする。
サーバ送信は非同期で、結果を待たない。実装は `index.html` の
`// ===== PUNCH-OUTBOX-BEGIN =====` 〜 `END` ブロックと `_execPunch`。

### 経路

```
打刻ボタン → doPunch()（既存の重複・順序チェック。_punchSaving 中は受け付けない）
           → _execPunch()  ※async
                ├ eventId 採番・実打刻時刻の確定（nr.timestamp/time/date）
                ├ await punchOutboxCommit(nr)      … IndexedDB へ保存
                │    └ false なら「打刻を保存できませんでした」＝打刻失敗。records に積まない
                ├ records.push(nr) / localStorage "tc5_records"（従来の打刻キャッシュ）
                ├ punchMsg / render()              … ここで画面が「打刻済み」
                └ punchOutboxFlush("punch")        … 送信。結果を待たない
```

★ **この3つの順序を崩してはならない。**

1. **サーバ応答を待って画面を更新してはならない。** 通信速度が打刻の体感時間に出る。
2. **IndexedDB への保存完了前に画面だけ打刻済みにしてはならない。**
   端末にもサーバにも無い打刻を「済んだ」と見せることになる。
3. **IndexedDB へ保存できなかったときは打刻失敗として扱う。**
   localStorage やサーバ直送へフォールバックしない（整合性を優先する）。
   `_execPunch` の `if(!_saved){…return;}` を消してはならない。

管理者の修正・追加（`saveRecord` / `patchRecord`）は従来どおりで、キューを通さない
（既にサーバにあるノードを編集する操作なので、存在確認つき再送とは意味が違う）。

### 保存構造（IndexedDB）

| 項目 | 値 |
|---|---|
| DB 名 | `timecard_punch_outbox`（version 1） |
| ストア | `punches`（`keyPath: "eventId"`） |
| エントリ | `{eventId, rec, state, createdAt, retryCount, lastAttemptAt, lastError}` |
| `state` | `"pending"`（送信待ち）/ `"syncing"`（送信中） |
| 送信成功時 | エントリを削除する（サーバに正本があるため端末に残さない＝ストアを小さく保つ） |

・`rec` は `tc5_records` へ書くレコードそのもの。
・**`localStorage` はキューの保存先として使わない。** 旧実装（2026-08-26 初版）が使っていた
　`tc5_punch_outbox` キーは、起動時に読み込んで IndexedDB へ移送したうえで削除する（移行処理）。
　`tc5_records` の端末キャッシュは従来どおりのキーを使う（本変更では触っていない）。
　★ ただし 2026-08-28 以降、中身は**全件ではなく取得済み区間分だけ**である（`mergeRecordsRange`）。
・**送信前に `state:"syncing"` を永続化する。** 送信中にアプリが終了しても、
　起動時に `pending` へ戻して再送できる（存在確認つきなので二重登録しない）。

### 二重登録が起きない理由

送信先は必ず `/tc5_records/{eventId}.json` への **PUT**。`eventId` は打刻時に端末が採番した
一意キーで、RTDB は「パスが主キー」なので、同じ `eventId` を何度 PUT しても1ノードを
上書きするだけで行は増えない。**これがサーバ側の一意制約の実体**であり、
PostgreSQL の `PRIMARY KEY` + `INSERT ... ON CONFLICT DO UPDATE` と同じ効果を構造が与える。

★ **`POST`（push）でサーバに採番させてはならない。** 再送のたびに別ノードができて支給に直結する。
★ **再送時に `eventId` を採り直してはならない。**

2回目以降の送信は **GET で存在確認してから書く**。これにより
「サーバには保存されたがクライアントが成功応答を受け取れなかった」打刻を再送しても、
上書きせず完了扱いにする（**管理者がその間に修正していても巻き戻さない**）。
★ **初回送信では存在確認しない**（毎回の打刻で通信を2倍にしないため）。
`punchOutboxFlush` が `retryCount` を増やす前に `isRetry` を判定して渡している。

`database.rules.json` は変更していない（変更は人間の確認が必要）。

### 時刻

| フィールド | 意味 |
|---|---|
| `timestamp` / `time` / `date` | **実際に打刻ボタンを押した時刻（端末時刻）。正本。再送しても変えない** |
| `serverReceivedAt` | サーバ（RTDB）が受け取った時刻。`{".sv":"timestamp"}` でサーバ側が入れる |
| `eventId` | 打刻イベントの一意キー（= `id` = 保存先ノード名） |

8:03 打刻 → 10:15 送信でも、正式な打刻時刻は **8:03**。
`tc5_records` に `created_at` 相当は無いため、サーバ受信時刻は `serverReceivedAt` を新設して持つ。
**追加フィールドはこの2つだけ**（`eventId` / `serverReceivedAt`）。既存行は両方とも持たない＝許容。
`serverReceivedAt` を含む PUT が 4xx で拒否された場合だけ、そのフィールドを外して1回だけ書き直す
（サーバ受信時刻は付加情報であり、打刻本体を落としてまで守らない）。

### 再送

契機: **打刻直後 / アプリ起動時・ページロード時 / `online` / `visibilitychange`（復帰）/ `pageshow` /
打刻画面の表示 / 10秒ポーリング**。

・間隔は 5s → 10s → 20s → 40s → 80s → 160s → 300s（上限）。
・**認証エラー（401/403）は最短60秒・上限10分**。叩いても通らないため通常より長く待つ。
　401/403 を成功扱いにせず、打刻も消さない。トークンは既存の更新周期で自動的に更新される。
・**通信復旧・起動・画面復帰はバックオフを待たない**（最低3秒だけあける）。
・**多重送信しない**: グローバルの実行中フラグ（`_punchOutboxFlushing`）＋各エントリの `"syncing"` 状態。
　`punch` / `online` / `visible` / `startup` が同時発火しても PUT は1回。
・通信断が出た時点でその回は打ち切る（順序維持・無駄な再試行の抑制）。
・**送信順は実打刻時刻の昇順**。オフライン中に 出勤→休憩開始→休憩終了→退勤 と打っても、この順で送る。

### 警告のしきい値と、その値にした理由

**最古の未送信が10分以上経過、または retryCount が8以上**のときだけ、
打刻画面とスタッフ選択画面に「⚠ 未送信の打刻があります（N件）」を出す。
通常の一時的な通信断では**何も表示しない**（送信中・送信待ち・同期中の常時表示はしない）。

根拠（2026-08-26 に本番実測した値から決めた。機械的に選んでいない）:

| 実測 | 値 |
|---|---|
| `tc5_records` 件数 | 4,188 件（2026-04-01 〜 2026-08-26） |
| 1日あたりの打刻 | 約 28 件（147日で 4,188 件） |
| 打刻あたりの端末滞在時間 | 約1.5秒（`punchTimer` で打刻後1.5秒でスタッフ選択画面へ戻る） |

・打刻した本人は**1.5秒後には画面を離れる**ため、数分後に出す警告は本人には届かない。
　警告の受け手は「次にその端末を使う人」と管理者であり、**早く出しても誰の役にも立たない**。
・一方で誤警報の代償は大きい（職員が管理者へ連絡する）。
　現場で起きる一時的な断は Wi-Fi ローミング（〜30秒）・ルータ再起動（1〜3分）で、
　**3分を超える断は「一時的ではない」**と判断できる。10分はその倍以上の余裕を取った値。
・1日28件・25人の運用では、実際の障害1回につき警告は1回出れば足りる。
　打刻ごとに出るような短いしきい値にすると、通信が不安定な日は終日警告が出続ける。
・`retryCount>=8` は時計がずれている端末向けの保険（バックオフ上、8回目は約10分に相当）。

**警告が出ていても打刻はできる**（バナー表示のみ。ボタンは止めない）。

### 端末に保存できないとき

`punchOutboxCommit` が false を返す＝打刻失敗。「打刻を保存できませんでした」を出し、
`records` にも積まない（＝画面は打刻前のまま。利用者はもう一度押せる）。
IndexedDB が開けない端末では、打刻画面とスタッフ選択画面に
**「⚠ この端末では打刻を保存できません」**を先出しする（押してから初めて気づく事態を避ける）。

★ この設計は「端末に保存できない端末では打刻できない」ことを意味する。
　プライベートブラウジング等で IndexedDB が使えない場合が該当する。
　**localStorage へのフォールバックは意図的に持たない**（要件どおり整合性を優先）。

### 未送信打刻を消さないための約束

サーバから `tc5_records` を取り直す箇所では、必ず `punchOutboxMergeInto(arr)` を通す。
通さないと**サーバ応答で `records` を差し替えた瞬間に未送信打刻が画面から消える**。
現在の直接呼び出しは2つ（起動時 `initFirebase`／`mergeRecordsRange()` の中）。
10秒ポーリングと朝出勤確認の「最新状態に更新」は `mergeRecordsRange()` 経由で間接的に通っている。
**`tc5_records` の再取得を新しく足すときは、同じ処理を必ず入れること。**
`punchOutboxMergeInto` は**サーバ側に同じ `eventId` があれば触らない**
（ローカルの古い内容でサーバの正本＝管理者修正後の値を上書きしない）。

### スタッフテスト画面・管理者デモ・閲覧用URLでは動かさない

`punchOutboxEnabled()` は `writePolicy==="full" && !viewerMode` のときだけ真。
テスト打刻を端末へ残して本番へ再送しないための境界であり、**緩めてはならない**。
無効時は従来どおり `saveRecord()` へ委譲する（sandbox の擬似成功・デモの遮断がそのまま働く）。

### 起動が通信断で止まらないようにした変更

・`initFirebase` 冒頭の `await getAuthToken()` を try/catch で包んだ。
　以前は通信断で例外になり `firebaseError=true` → **「通信エラーです」画面でスタッフを選べず、打刻自体ができなかった**。
・上記で通信断時もスタッフ選択へ到達できるため、`staffPinsLoaded` を追加した。
　`tc5_pins` を**取得できていない状態では「PIN未登録」と断定できない**ため、PIN新規登録へ進めず案内だけ出す。
　★ これが無いと、PIN未取得のまま新規登録して `staffPins={本人だけ}` を `/tc5_pins` へ全置換PUTし、
　**他スタッフのPINを全消しする**（`saveData("tc5_pins", …)` は全体PUT）。この経路は変更前から存在した。
・`tc5_pins` の取得は `r.ok` を確認する（「取得成功して不在」と「取得失敗」を区別する）。

### 既知の制限（未解消・運用で認識しておくこと）

1. **完全オフラインでの「アプリ再起動後の新規ログイン」はできない。**
   PIN照合材料（`tc5_pins`）は仕様上 localStorage へ保存しない。4桁PINのハッシュは総当たりで復元できるため、
   端末保存は認可の後退になる。オフライン時は案内を出して止める。
   **すでにログイン済み（打刻画面を開いたまま）の打刻・ページ更新後の未送信保持・復旧後の自動送信は動作する。**
2. **端末時刻がずれていると打刻時刻もずれる**（変更前から同じ）。
   `serverReceivedAt` と突き合わせれば事後に検出できる（`scripts/verify-punch-events.js` の判定4）。
3. **未送信のまま端末を初期化・ブラウザデータを削除すると打刻は失われる。** 端末保存の性質上避けられない。
   警告表示が唯一の検知手段なので、**しきい値を緩める変更をしてはならない**。
4. **IndexedDB が使えない端末では打刻できない**（上記「端末に保存できないとき」）。

### DB 変更・rollback・verify

・**migration ファイルは無い**（Firebase RTDB はスキーマレス。Type C）。
　増えるのは新規打刻に付く追加フィールド2つ（`eventId` / `serverReceivedAt`）だけで、
　既存行への一括更新は**不要かつ行ってはならない**。
・**rollback**: コードを revert するだけでよい。既に書かれた `eventId` / `serverReceivedAt` は
　既存の集計・修正・監査が参照しないため残っていても無害。データの巻き戻しは不要。
・**verify**: `node scripts/verify-punch-events.js`（読み取り専用）。
　`FIREBASE_API_KEY` / `FIREBASE_DATABASE_URL` を環境変数で渡す。
　ノード名と `id` の一致・`eventId` の重複・サーバ受信時刻の妥当性を確認する。
　★ `tc5_records` には**旧実装（全件を配列で PUT していた時代）の行がキー＝配列添字で 1,727 件**残っている。
　これは既知の既存データで、verify は判定対象から除外する（2026-08-26 実測）。
